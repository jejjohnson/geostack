Three kinds of function, three kinds of data

How code in the stack is packaged (function, Module, Operator), what data it sees (array, named array, carrier), and the role each name plays in its library's API, from structures up to recipes. This page holds the problem, the objects in symbols, the role ladder, who works where, one vocabulary per axis, and the rules that follow. The layer map keeps the layers, the imports and the boundaries of each library, and links here.

The problem: why geo code is hard to write well

Take one running example: a cloud-masked NDVI time series from a stack of Sentinel-2 scenes, gap-filled, then sampled at flux-tower sites. Every step of it can go wrong in a way that raises no error.

ProblemWhat goes wrong, silentlyWhat fixes it
Axes by positionOne reader returns (band, y, x), another (y, x, band); time is first in one file and last in the next. mean(axis=0) averages over the wrong thing and returns a plausible number.named array: dims by name, mean("time")
Lost georeferencenp.asarray(scene)[..., 100:200, 50:150] keeps the pixels and drops the transform. Rewrapped with the scene's transform, the crop claims to start at the scene's corner, and the tower sites land on the wrong pixels.carrier: slicing moves the transform with the data
Mismatched gridsTwo rasters with the same shape but a half-pixel shift, or another CRS, combine pixel by pixel into a smeared result.carrier: require_grid_match refuses

The fixes split cleanly. The first four problems are about the data; the last three are about how the code is packaged. That is why the stack has two axes.

The objects, in symbols

The whole stack rests on two ideas: a function of arrays, 𝐲=f(𝐱,𝐮;𝜽)\vect{y} = f(\vect{x}, \vect{u}; \gvect{\theta}), and an Operator that lifts that function onto geographic data, h[f,𝜽](𝐱geo;α)h[f, \gvect{\theta}](\vect{x}_\text{geo}; \alpha). Everything else is bookkeeping about what the data knows and where the settings live. The symbols, each defined in full with its shape in the sections below:

  • 𝐱\vect{x}: the data as a plain array of numbers; 𝐲\vect{y}: the array the function returns.
  • 𝐮\vect{u}: what the function needs to know about where the data sits, as plain arrays or integers: cell areas, latitudes, a transform, the position of a named band. It is read off the data, never fitted.
  • 𝜽∈ℝDθ\gvect{\theta} \in \mathbb{R}^{D_\theta}: the function's parameters, set when the Operator is built and constant over a call (a threshold, a scale, fitted weights); empty for NDVI.
  • ff: the function itself, which sees only 𝐱\vect{x}, 𝐮\vect{u} and 𝜽\gvect{\theta}.
  • 𝐱geo\vect{x}_\text{geo}: the same data as a carrier, the array together with its axis names, coordinates and georeference.
  • α\alpha: the Operator's config, names and settings only (which bands, which dimension, the fill policy), so it round-trips through JSON.
  • h[f,𝜽]h[f, \gvect{\theta}]: the Operator built from ff and 𝜽\gvect{\theta}; called on a carrier with config α\alpha, it unwraps, calls ff, and rewraps. Written h[f]h[f] when 𝜽\gvect{\theta} is empty.

Two axes follow from those ideas: what the data knows (𝐱\vect{x} or 𝐱geo\vect{x}_\text{geo}), and how the code is packaged (ff, a Module, or h[f,𝜽]h[f, \gvect{\theta}]).

The running example is a stack of Sentinel-2 scenes: NtimeN_\text{time} acquisition dates, NbandN_\text{band} bands and Nrow×NcolN_\text{row} \times N_\text{col} pixels, turned into a cloud-masked NDVI time series, gap-filled, and sampled at flux-tower sites. Its dimension names follow geoarray, ("time", "band", "y", "x"); the sizes are written NrowN_\text{row} and NcolN_\text{col} so that 𝐲\vect{y} stays the output of a function.

The data axis: what 𝐱\vect{x} knows

▦ Plain array

A block of numbers with a shape and nothing else:

𝐱∈ℝN1×…×NNax\vect{x} \in \mathbb{R}^{N_1 \times \ldots \times N_{N_\text{ax}}}
  • NaxN_\text{ax}: the number of axes; a=1,…,Naxa = 1, \ldots, N_\text{ax} indexes them.
  • NaN_a: the length of axis aa.

Example The scene stack is 𝐱∈ℝNtime×Nband×Nrow×Ncol\vect{x} \in \mathbb{R}^{N_\text{time} \times N_\text{band} \times N_\text{row} \times N_\text{col}}, so Nax=4N_\text{ax} = 4. Which axis is time is a convention the code has to remember: a mean over axis 1 is a mean over time only if every reader put time first. One reader returns (band, y, x), another (y, x, band), and the wrong mean runs without an error.

In code a NumPy or JAX array. Its axis order lives in a jaxtyping annotation and in each einx pattern, so the convention is written down at every call, but nothing checks it against the data: a stack read as (band, y, x, time) passes the same call and averages over the wrong axis.

import einx
import jax.numpy as jnp
import numpy as np
from jaxtyping import Array, Float


def time_mean(stack: Float[Array, "time band y x"]) -> Float[Array, "band y x"]:
    """Mean of a scene stack over its acquisition dates.

    x̄ = (1 / N_time) ∑_t x_t
    """
    # the axis names live in this pattern and the annotation, not in the data
    mean_scene = einx.mean("[time] band y x", stack)
    return mean_scene


# x ∈ ℝ^(N_time × N_band × N_row × N_col), on the host
reflectance = np.zeros((4, 13, 600, 600), dtype=np.float32)
# the same numbers on the device
stack = jnp.asarray(reflectance)
mean_scene = time_mean(stack)

▤ Named array

The same numbers with a name dad_a and a coordinate vector 𝐜a\vect{c}_a for each axis:

𝐱named=(𝐱,𝐝,𝒞)\vect{x}_\text{named} = (\vect{x}, \vect{d}, \mathcal{C})
𝐝=(d1,…,dNax)\vect{d} = (d_1, \ldots, d_{N_\text{ax}})
𝒞=(𝐜1,…,𝐜Nax)\mathcal{C} = (\vect{c}_1, \ldots, \vect{c}_{N_\text{ax}})
  • 𝐝\vect{d}: one name per axis, all distinct.
  • 𝐜a∈ℝNa\vect{c}_a \in \mathbb{R}^{N_a}: the coordinates along axis aa (dates, wavelengths, positions).

An operation addresses an axis by name, and the array finds its position. Take a reduction rar_a (a mean, a sum, a maximum) over axis aa of a plain array: it maps ℝN1×…×NNax\mathbb{R}^{N_1 \times \ldots \times N_{N_\text{ax}}} to the same space with the factor NaN_a left out. On a named array the same reduction is asked for by a name dd. The array looks up its position, a=pos𝐝(d)a = \op{pos}_{\vect{d}}(d), reduces there, and removes that axis's name and coordinates, since the output no longer has that axis:

rd(𝐱named)=(ra(𝐱),𝐝−a,𝒞−a)r_d(\vect{x}_\text{named}) = (r_a(\vect{x}), \vect{d}_{-a}, \mathcal{C}_{-a})
𝐝−a=(d1,…,da−1,da+1,…,dNax)\vect{d}_{-a} = (d_1, \ldots, d_{a-1}, d_{a+1}, \ldots, d_{N_\text{ax}})
𝒞−a=(𝐜1,…,𝐜a−1,𝐜a+1,…,𝐜Nax)\mathcal{C}_{-a} = (\vect{c}_1, \ldots, \vect{c}_{a-1}, \vect{c}_{a+1}, \ldots, \vect{c}_{N_\text{ax}})
  • pos𝐝(d)\op{pos}_{\vect{d}}(d): the position of the name dd in 𝐝\vect{d}; an error if dd is not there.
  • 𝐝−a\vect{d}_{-a}, 𝒞−a\mathcal{C}_{-a}: the names and coordinates with entry aa taken out.

Example 𝐝=(𝚝𝚒𝚖𝚎,𝚋𝚊𝚗𝚍,𝚢,𝚡)\vect{d} = (\texttt{time}, \texttt{band}, \texttt{y}, \texttt{x}), with 𝐜1\vect{c}_1 the acquisition dates. mean("time") finds pos𝐝(𝚝𝚒𝚖𝚎)=1\op{pos}_{\vect{d}}(\texttt{time}) = 1, averages over axis 1, and returns names (𝚋𝚊𝚗𝚍,𝚢,𝚡)(\texttt{band}, \texttt{y}, \texttt{x}) without the dates, whatever order the reader used.

In code pipekit-array's DimArray: the data, one name per axis, and static labels on the dims that have them (here the band names), with no other coordinates. It is a JAX pytree whose only leaf is the data, so new values never recompile. An xarray DataArray is the same object with full coordinates, and pipekit's dim functions (reduce, sel, isel, transpose) run on both through their adapters.

import numpy as np
import pipekit_array as pa

reflectance = np.zeros((4, 13, 600, 600), dtype=np.float32)

SENTINEL2_BANDS = tuple("B01 B02 B03 B04 B05 B06 B07 B08 B8A B09 B10 B11 B12".split())

# x_named = (x, d, C): one name per axis, static labels on the band dim
stack = pa.DimArray(reflectance, ("time", "band", "y", "x"), {"band": SENTINEL2_BANDS})
# r_time: the mean over the dim named "time", wherever it sits
mean_scene = pa.reduce(stack, "mean", "time")
# x at the label B04; a single label drops its dim
red = pa.sel(stack, band="B04")

◆ Carrier

A named array plus its georeference Γ\Gamma:

𝐱geo=(𝐱named,Γ)\vect{x}_\text{geo} = (\vect{x}_\text{named}, \Gamma)
Γ=(crs,𝐀,xfill,ℳ)\Gamma = (\op{crs}, \mat{A}, x_\text{fill}, \mathcal{M})
  • crs\op{crs}: the coordinate reference system (an EPSG code or WKT).
  • 𝐀∈ℝ2×3\mat{A} \in \mathbb{R}^{2 \times 3}: the affine transform from pixel to map coordinates.
  • xfill∈ℝx_\text{fill} \in \mathbb{R}: the fill value, NaN allowed.
  • ℳ\mathcal{M}: the attributes (units, sensor, processing level). Band names and wavelengths are coordinates of the band axis, in 𝒞\mathcal{C}.

The transform says where each pixel is. The top-left corner of the pixel in row ii and column jj sits at map coordinates 𝐬ij∈ℝ2\vect{s}_{ij} \in \mathbb{R}^2, and its centre at (j+1/2,i+1/2)(j + 1/2, i + 1/2) in pixel units:

𝐬ij=𝐀(ji1)\vect{s}_{ij} = \mat{A} \begin{pmatrix} j \\ i \\ 1 \end{pmatrix}

The fill value says which pixels are missing. A pixel is valid when every entry there, over all bands and dates, is finite and differs from the fill, which gives the valid mask 𝐦∈{0,1}Nrow×Ncol\vect{m} \in \{0, 1\}^{N_\text{row} \times N_\text{col}}, with tt indexing dates and bb bands:

[𝐦]ij=∏t=1Ntime∏b=1Nband𝟏[xt,b,i,j≠xfill]𝟏[xt,b,i,j is finite][\vect{m}]_{ij} = \prod_{t=1}^{N_\text{time}} \prod_{b=1}^{N_\text{band}} \mathbf{1}[x_{t,b,i,j} \neq x_\text{fill}] \mathbf{1}[x_{t,b,i,j} \text{ is finite}]

For a swath or a curvilinear grid, 𝐀\mat{A} is replaced by per-pixel coordinates 𝐒lon,𝐒lat∈ℝNrow×Ncol\mat{S}_\text{lon}, \mat{S}_\text{lat} \in \mathbb{R}^{N_\text{row} \times N_\text{col}}; the rest is the same.

Example The scene is a carrier on a UTM grid with xfill=0x_\text{fill} = 0 and band names B01 to B12 in 𝒞\mathcal{C}. A tower at map coordinates 𝐬\vect{s} is found at pixel (i,j)(i, j) by solving 𝐬=𝐀(j,i,1)⊤\vect{s} = \mat{A} (j, i, 1)^\top for (i,j)(i, j), which is to_pixel. Slice the bare array instead, np.asarray(scene)[..., 100:200, 50:150], and 𝐀\mat{A} still describes the full scene: the crop claims to start at the scene's corner, and every tower lands on the wrong pixel.

In code geotoolz-array's GeoArray: the data (NumPy or JAX), its dims ending in ("y", "x"), coordinates for the other dims (TimeAxis, SpectralAxis), the transform, CRS, fill value and frozen attrs. Slicing, crop and read_window move the transform with the pixels. GeoSwath carries per-pixel latitude and longitude instead of a transform, and GeoPoints a set of points; xrops plays the same role for a DataArray whose coordinates and CRS mean geography.

import numpy as np
import pipekit_array as pa
from geoarray import GeoArray, crop, to_pixel
from geoarray.coords import SpectralAxis, TimeAxis

reflectance = np.zeros((4, 13, 600, 600), dtype=np.float32)

SENTINEL2_BANDS = tuple("B01 B02 B03 B04 B05 B06 B07 B08 B8A B09 B10 B11 B12".split())

WAVELENGTHS_NM = (443, 490, 560, 665, 705, 740, 783, 842, 865, 945, 1375, 1610, 2190)

# C: the acquisition dates, and the band names with their centre wavelengths
dates = TimeAxis(
    stamps=np.array(["2026-06-01", "2026-06-06", "2026-06-11", "2026-06-16"])
)
bands = SpectralAxis(names=SENTINEL2_BANDS, wavelength_nm=WAVELENGTHS_NM)
# x_geo = (x_named, Γ), Γ = (crs, A, x_fill, M): a 10 m grid in UTM zone 30N
scene = GeoArray(
    reflectance,
    (10.0, 0.0, 600000.0, 0.0, -10.0, 4400000.0),
    "EPSG:32630",
    fill_value=0.0,
    dims="time band y x",
    coords=(dates, bands),
)
# m: valid where every band on every date is finite and differs from the fill
valid = scene.valid_mask()
# the same named reduction as on a DimArray; the result keeps Γ
mean_scene = pa.reduce(scene, "mean", "time")
# s = A (j + ½, i + ½, 1)ᵀ, solved for the fractional (i, j) of each tower
tower_xy = np.array([[600105.0, 4399895.0], [602340.0, 4398110.0]])
tower_pixels = to_pixel(scene.transform, tower_xy)
# a crop from row 100, column 50 moves A with the pixels
window = crop(scene, (100, 50), (100, 100))

The kind axis: how ff is packaged

ƒ Function

A pure function of arrays, with its parameters passed in on every call:

𝐲=f(𝐱,𝐮;𝜽)\vect{y} = f(\vect{x}, \vect{u}; \gvect{\theta})
  • 𝐱\vect{x}: the input array; 𝐲\vect{y}: the output array.
  • 𝐮\vect{u}: what ff needs to know about where the data sits, as plain arrays or integers (cell areas, latitudes, a transform, band positions).
  • 𝜽∈ℝDθ\gvect{\theta} \in \mathbb{R}^{D_\theta}: parameters, constant over the call; empty for NDVI.

ff never sees a name, a CRS or a fill value. That is what lets it run under jit, on any carrier, in any library below GeoStack.

Example NDVI on the bare stack. It has no parameters; what it needs from the data is where the two bands are, 𝐮=(ured,unir)∈{1,…,Nband}2\vect{u} = (u_\text{red}, u_\text{nir}) \in \{1, \ldots, N_\text{band}\}^2:

fndvi(𝐱,𝐮)=𝐱unir−𝐱ured𝐱unir+𝐱uredf_\text{ndvi}(\vect{x}, \vect{u}) = \frac{\vect{x}_{u_\text{nir}} - \vect{x}_{u_\text{red}}}{\vect{x}_{u_\text{nir}} + \vect{x}_{u_\text{red}}}

Here 𝐱ured∈ℝNtime×1×Nrow×Ncol\vect{x}_{u_\text{red}} \in \mathbb{R}^{N_\text{time} \times 1 \times N_\text{row} \times N_\text{col}} is the stack at one band position, the division is element by element, and the output has one band.

def ndvi(
    reflectance: Float[Array, "*time band y x"],
    *,
    red: int,
    nir: int,
) -> Float[Array, "*time 1 y x"]:
    """Normalised difference vegetation index of a red and a near-infrared band.

    NDVI = (x_nir − x_red) / (x_nir + x_red)
    """
    # x_red, keeping a singleton band axis
    red_band = reflectance[..., red : red + 1, :, :]
    # x_nir
    nir_band = reflectance[..., nir : nir + 1, :, :]
    # x_nir − x_red
    difference = nir_band - red_band
    # x_nir + x_red
    total = nir_band + red_band
    # (x_nir − x_red) / (x_nir + x_red)
    index = difference / total
    return index

▣ Module

A function with state. A setup step builds the state 𝝍\gvect{\psi} once, from data 𝐗\mat{X}, and may do work that cannot be traced (a k-NN graph, a triangulation, a factorisation). The call is then pure and jittable:

𝝍=setup(𝐗;𝜽)\gvect{\psi} = \op{setup}(\mat{X}; \gvect{\theta})
𝐲=f(𝐱,𝐮;𝜽,𝝍)\vect{y} = f(\vect{x}, \vect{u}; \gvect{\theta}, \gvect{\psi})
  • 𝐗\mat{X}: the data setup sees, one row per sample (for the gap-fill, the coordinates of the valid pixels).
  • 𝝍\gvect{\psi}: the state, a pytree of arrays held as the Module's fields next to 𝜽\gvect{\theta}.

Example The gap-fill. With n=1,…,NrowNcoln = 1, \ldots, N_\text{row} N_\text{col} indexing pixels and q=1,…,Nnbq = 1, \ldots, N_\text{nb} their neighbours, setup builds the neighbour map nb(n,q)\op{nb}(n, q) over the valid pixels and the weights 𝐖∈ℝNrowNcol×Nnb\mat{W} \in \mathbb{R}^{N_\text{row} N_\text{col} \times N_\text{nb}}, rows summing to one. Each call is a weighted mean:

yn=∑q=1Nnb[𝐖]nqxnb(n,q)y_n = \sum_{q=1}^{N_\text{nb}} [\mat{W}]_{nq} x_{\op{nb}(n, q)}
class NeighbourFill(eqx.Module):
    """Fill every pixel with a weighted mean of its nearest valid pixels.

    y_n = ∑_q W_nq x_nb(n,q), with the graph nb built once, outside jit.
    """

    neighbours: Int[Array, "pixel neighbour"]
    weights: Float[Array, "pixel neighbour"]

    @classmethod
    def fit(
        cls, valid_mask: Bool[np.ndarray, "y x"], *, n_neighbours: int
    ) -> "NeighbourFill":
        # --- setup: host-side NumPy and SciPy, runs once ---
        # (i, j) of every pixel, one row each
        grid = np.indices(valid_mask.shape)
        coordinates = einx.rearrange("two y x -> (y x) two", grid)
        # X: the coordinates of the valid pixels
        is_valid = einx.rearrange("y x -> (y x)", valid_mask)
        valid_coordinates = coordinates[is_valid]
        # nb(n, q): the n_neighbours nearest valid pixels of pixel n
        tree = scipy.spatial.cKDTree(valid_coordinates)
        distance, nearest = tree.query(coordinates, k=n_neighbours)
        valid_index = np.flatnonzero(is_valid)
        neighbours = valid_index[nearest]
        # W_nq ∝ 1 / (1 + distance), each row summing to one
        inverse = 1.0 / (1.0 + distance)
        row_total = einx.sum("pixel [neighbour]", inverse)
        weights = einx.divide(
            "pixel neighbour, pixel -> pixel neighbour", inverse, row_total
        )
        return cls(neighbours=jnp.asarray(neighbours), weights=jnp.asarray(weights))

    def __call__(self, field: Float[Array, "y x"]) -> Float[Array, "y x"]:
        # --- every call: pure and jittable ---
        flat = einx.rearrange("y x -> (y x)", field)
        # x_nb(n,q)
        gathered = flat[self.neighbours]
        # y_n = ∑_q W_nq x_nb(n,q)
        filled = einx.dot(
            "pixel neighbour, pixel neighbour -> pixel", self.weights, gathered
        )
        return einx.rearrange("(y x) -> y x", filled, y=field.shape[0])

→ Operator

A pipeline step that lifts ff onto carriers. The Operator h[f,𝜽]h[f, \gvect{\theta}] is built from the function and its parameters; it is called on a carrier with its config α\alpha, a JSON record (which bands, which dimension, the fill policy). It unwraps the carrier with πα\pi_\alpha, calls ff on plain arrays, and rewraps with ια\iota_\alpha:

h[f,𝜽](𝐱geo;α)=ια(f(πα(𝐱geo);𝜽),𝐱geo)h[f, \gvect{\theta}](\vect{x}_\text{geo}; \alpha) = \iota_\alpha(f(\pi_\alpha(\vect{x}_\text{geo}); \gvect{\theta}), \vect{x}_\text{geo})
πα(𝐱geo)=(𝐱,𝐮)\pi_\alpha(\vect{x}_\text{geo}) = (\vect{x}, \vect{u})

Read the first line from the inside out: πα\pi_\alpha unwraps, ff computes, ια\iota_\alpha rewraps. The unwrap hands down the array and what ff needs to know about it, 𝐮\vect{u}, with every name in α\alpha already resolved against the carrier's names and coordinates. 𝜽\gvect{\theta} passes through untouched; α\alpha never reaches ff. The rewrap builds the output carrier:

ια(𝐲,𝐱geo)=𝐲geo=((𝐲,𝐝y,𝒞y),Γy)\iota_\alpha(\vect{y}, \vect{x}_\text{geo}) = \vect{y}_\text{geo} = ((\vect{y}, \vect{d}_y, \mathcal{C}_y), \Gamma_y)
Γy={Γsame gridregridα(Γ)new grid\Gamma_y = \begin{cases} \Gamma & \text{same grid} \\ \op{regrid}_\alpha(\Gamma) & \text{new grid} \end{cases}
  • α\alpha: the config, names and settings only, so it round-trips through JSON.
  • πα\pi_\alpha, ια\iota_\alpha: the unwrap and the rewrap, both read α\alpha; ια\iota_\alpha also takes the input carrier, whose georeference the output inherits or regrids.
  • 𝐝y\vect{d}_y, 𝒞y\mathcal{C}_y, Γy\Gamma_y: the output's names, coordinates and georeference.
  • regridα\op{regrid}_\alpha: the input grid to the output grid, for a reprojection or a resampling.

Operators compose: h[f2,𝜽2](h[f1,𝜽1](𝐱geo;α1);α2)h[f_2, \gvect{\theta}_2](h[f_1, \gvect{\theta}_1](\vect{x}_\text{geo}; \alpha_1); \alpha_2) is what pipekit writes step1 | step2, each step holding its own 𝜽\gvect{\theta} and α\alpha.

Example The settings are band names, α={red:𝙱𝟶𝟺,nir:𝙱𝟶𝟾}\alpha = \{\text{red}: \texttt{B04}, \text{nir}: \texttt{B08}\}, and πα\pi_\alpha turns them into the positions 𝐮=(4,8)\vect{u} = (4, 8) by looking them up in the band coordinate of 𝒞\mathcal{C}. ια\iota_\alpha returns a carrier on the same grid, Γy=Γ\Gamma_y = \Gamma, with one band named ndvi and NaN written where [𝐦]ij=0[\vect{m}]_{ij} = 0. That is geoops.indices.NDVI(red="B04", nir="B08").

class NDVI(pipekit.Operator):
    """NDVI on a carrier: unwrap, call ndvi on arrays, rewrap on the same grid."""

    def __init__(self, *, red: str = "red", nir: str = "nir") -> None:
        # α: names only, so the config round-trips through JSON
        self.red = red
        self.nir = nir

    def _apply(self, scene: GeoArray["*time band y x"]) -> GeoArray["*time band y x"]:
        # π_α: names in α → positions u, through the band coordinate in C
        red = resolve_band(scene, self.red)
        nir = resolve_band(scene, self.nir)
        # f(x, u) on plain arrays
        index = ndvi(np.asarray(scene), red=red, nir=nir)
        # ι_α: same grid, one band named "ndvi", NaN where the scene was invalid
        return wrap_like(scene, index, band_names=("ndvi",), fill_value=np.nan)

The function and the Module are illustrations; the Operator follows geoops' conventions (resolve_band, wrap_like), with signatures simplified.

Three steps, each a lifted function, in one recipe:

𝐳geo=h[fndvi](𝐱geo;α1)\vect{z}_\text{geo} = h[f_\text{ndvi}](\vect{x}_\text{geo}; \alpha_1)

Here 𝐳geo\vect{z}_\text{geo} is the NDVI carrier, 𝐰geo\vect{w}_\text{geo} the gap-filled one and 𝐲geo\vect{y}_\text{geo} the values at the towers; 𝝍\gvect{\psi} is the fill's state.

Code in the stack is packaged as one of three kinds: a function, a Module or an Operator. Each kind can work on one of three kinds of data: plain arrays, named arrays, or carriers. These are two separate axes. geoarray is not a fourth kind; it sits on the data axis. Names in italics are proposed.

The data axis in three lines

▦ A plain array 𝐱\vect{x} knows its shape.

▤ A named array 𝐱named=(𝐱,𝐝,𝒞)\vect{x}_\text{named} = (\vect{x}, \vect{d}, \mathcal{C}) knows which axis is which.

◆ A carrier 𝐱geo=(𝐱named,Γ)\vect{x}_\text{geo} = (\vect{x}_\text{named}, \Gamma) also knows where each pixel is (𝐀\mat{A}), and which pixels are missing (xfillx_\text{fill}, 𝐦\vect{m}).

So a carrier is a named array plus its georeference. The named array still earns its place: it is the protocol that lets one Operator (Reduce(dim="time")) run on DimArray, DataArray and GeoArray through their adapters, and it is the end product for data with dims but no geography: a DA ensemble (member, time, state), a sweep, a posterior summary.

"Kicking a Module up a notch" is two separate steps. Wrapping it in an Operator adds composition: a config, |, graph mode. Moving it to carriers adds georeference: the CRS, the fill, the attrs. The steps are independent. JaxModelOp and a DA cycle take the first step without the second; geoarray's crop and read_window take the second without the first. geoops Operators take both.

Inside a library: the role ladder

gaussx draws its API as a ladder: primitives, operators, strategies, distributions, recipes. The same ladder fits every library in the stack, and it sits across the three kinds rather than beside them. Read it as grammar, from ⓪ down: structures are the nouns (Kronecker, and the data itself: arrays, named arrays, carriers), primitives the verbs that act on them (solve), strategies the adverbs that say how (CGSolver), models the noun phrases (a Gaussian with this mean), algorithms the sentences (kalman_filter), steps (pipekit Operators) a sentence with its own settings, ready to chain (NDVI), and recipes the paragraphs: steps composed into one job, from source to product. Above the ladder, orchestration runs recipes; it is not a rung. Module is not a rung; it is how three rungs are packaged: ⓪ structures, ② strategies and ③ models. Its setup step setup\op{setup}, which builds state from data outside the jitted path, is what gaussx draws as the sidebar of tools that produce operators. Rungs are marked with circled digits, ⓪ to ⑥, so they cannot be confused with tiers (T) or processing levels (L); names in italics are proposed.

Why structures sit below primitives. In gaussx, _primitives imports _operators 76 times and _operators imports _primitives once: the verbs exist to dispatch on the nouns. With the nouns at the floor, the ladder is also the build order. One entanglement is left: a primitive takes a strategy argument (solve(A, b, solver=CGSolver())) and some strategies call primitives (diag, trace); _primitives and _strategies import each other eight times each way. That pair is gaussx's dispatch core, now its only documented exception.

The data are nouns too. ▦ arrays, ▤ named arrays and ◆ carriers are the ⓪ structures of the data axis: DimArray is pipekit-array's noun, GeoArray, GeoSwath and GeoPoints are geoarray's, and geoarray's own verbs (crop, to_pixel, read_window) are the ① primitives that act on them. The kind and data axes say how a noun is packaged and what it knows; the ladder says it is a noun.

Steps and recipes. The test between ⑤ and ⑥: does it do one thing to its input, or does it put steps (its own, or ones you pass in) in order to make a job? NDVI and Reproject are steps; load, reproject, patch, rescale and NDVI, from a Sentinel-2 L2A scene to an NDVI COG, is a recipe. What counts is how it is built, not its name or what it does inside: Reproject resamples and warps internally but is one closed class with settings, so it is a step, and so is geoops.viz.RGBRecipe despite its name (RGBComposite would say it better). Some recipes ship in libraries as templates, compositions with slots for your steps: DACycle (forecast then analysis, cycled), TrainingLoop, and the patcher's split, process and stitch. The combinators (Sequential, Graph, Branch, Retry) are the conjunctions that join steps, so they sit at ⑥ too.

Composition is closed; running is not. A recipe of recipes is a recipe, as a Sequential of Sequentials is a Sequential, so the ladder stops at ⑥. What sits above is not more composition but running it: which items, when, where, with what retries and storage. That is orchestration, the application's job (a DVC stage, an Airflow or Prefect flow, a FastAPI endpoint, GeoApps), and the same recipe should run unchanged in all of them. A recipe has two forms, code (a Sequential or Graph built in Python) and data (a YAML file that pipekit.loads reads back). The data form needs every step in it to round-trip (a strict-JSON get_config, from_state, no live objects), and a recipe that comes from a user goes through loads_sandboxed with an allowlist: a recipe that names classes is code. Settings composed with Hydra override values inside a recipe; they do not become a second recipe format.

Against gaussx's own numbering: its L1 operators become ⓪ structures and its L0 primitives ① primitives (the swap above); L1.5, L2 and L3 become ② strategy, ③ model (its "distributions", renamed so the rung reads the same in libraries with none: a functax plan, a kernellib estimator, a sesmax model) and ④ algorithm; ⑤ step and ⑥ recipe are pipekit's. gaussx's word "recipes" moves up the ladder: in the stack a recipe is a composition of steps, as in a kitchen, in Pangeo Forge's ETL recipes and in torchtune's training recipes. UnscentedIntegrator moves from gaussx's recipes to the strategies: it is a choice of how to integrate, like CGSolver is a choice of how to solve.

Who works where: bands of the ladder

Each kind of user works in a band of the ladder and treats the rung below it as atomic: their floor. A geoscientist calls NDVI and never opens it; an ML researcher calls solve and never opens it. The word is floor, not primitive: ① stays one role, the same for everyone.

Carriers start at ⑤, but ⑤ does not need carriers. Nothing below ⑤ computes on a carrier: that is the second of the three invariants under rule 3, nothing below GeoStack sees 𝐱geo\vect{x}_\text{geo}, only πα\pi_\alpha(𝐱geo\vect{x}_\text{geo}). A step is exactly where πα\pi_\alpha and ια\iota_\alpha happen, so geo territory begins there. The converse does not hold: JaxModelOp, a DA cycle and a training loop are steps and recipes on plain arrays. Geo territory is ⑤ and ⑥ with carrier data. geoarray's own nouns and verbs (GeoArray, crop, to_pixel) sit at ⓪ and ① but handle georeference only and compute no field. On the xarray side, geoscientists call functions on named arrays (xrops), so their floor is set by the data as much as by the rung.

Floors leak, so design for one rung down. When a step's settings fall short, a geoscientist should reach the algorithm it wraps without reading its source: every step's docstring names the function it calls (the f in liftα[f]). Errors speak the band's language: band names, CRS and fill at ⑤ and ⑥, shapes at ④ and below. Docs open by band, one entry point per kind of user, not one per library. And ⑤ and ⑥ are the API the most people touch, so they get the strictest deprecations.

How the axes constrain each other. The role fixes the kind: ① and ④ are functions, ⓪, ② and ③ are Modules (or, at ⓪, a third-party array), ⑤ and ⑥ are Operators (a recipe in code is a Sequential or Graph, itself an Operator; in data, the YAML that loads into one), so a library's chips only need the digit. The kind and the data fix the lowest layer. Inside one library, imports follow the roles upward, nouns first; the one entanglement left is between verbs and adverbs (a primitive takes a strategy; some strategies call primitives), which gaussx documents as its dispatch core.

What this retires. The kind once called "primitive" is now "function", so "primitive" names one role (①) only. geostack's docs/design/stack_levels.md L1 to L3 (primitives and machinery, operators on carriers, pipelines) were a mix of kind and data; the glyph pairs say the same without a number (ƒ ▣ on ▦; → on ◆; ⑤ steps composed into ⑥ recipes). Two words stay where the field uses them on purpose: "linear operator" (lineax's AbstractLinearOperator, a ⓪ structure) and "observation operator" (H). Capital-O Operator means pipekit's kind only.

Which cell is it?

  1. Kind. Does it subclass pipekit.Operator? Then it is an Operator, whatever else it inherits; JaxOperator is also an eqx.Module and is still an Operator. Else, is it a class whose setup does work before a pure call? A Module. Else it is a function.
  2. Data. Does it take or return a CRS, a fill or attrs? Carrier. Dims with names and coordinates, but no CRS? Named array. Neither? Plain array.

Do we need a name change?

Not in code; in prose, yes. In code the namespaces already separate the two kinds of operator (lineax calls its own AbstractLinearOperator), and renaming pipekit.Operator would touch pipekit, every geoops and xrops class, vardax, plumax and sesmax, all for a prose problem. "Observation operator" is the field's own word for H and stays. In prose: function for the kind (not "kernel", which kernellib uses for covariance functions, nor "primitive", which now names the ① role), Module, Operator with a capital O for pipekit's, and carrier for the data. The full vocabulary, one per axis, is in the box under the role ladder. The suffix rules on the library cards of the layer map keep the class names apart as well.

Rule 2: the tier decides what a library may import

Unchanged: a library imports any lower layer, and lower tiers of its own layer. A tier never changes which kinds a library may define. pipekit and gaussx are both Core tier 0, yet one defines Operators and the other Modules; the cells come from the layer.

Three invariants

Arrays go everywhere. Every kind takes them.

Carriers stop at GeoStack. An Operator on carriers unwraps before it calls down and rewraps on the way back; nothing below GeoStack takes a carrier as input, and that includes xarray.DataArray. One narrow exception, listed by name with its reason:

An export at the edge. A method that only returns results as a labelled container (to_xarray), imports it lazily behind an extra, attaches no CRS, and is called by nothing else in the library. Carriers flowing out at the end couple nothing; carriers flowing in are what the rule stops.

Configs stop at Operators. Hydra and JSON configs build Operators and apps; Modules and functions take plain values (numbers, arrays, other Modules), never a DictConfig.

Rule 4: each library declares its cells

Every row of the boundaries table on the layer map carries the kinds and data that library exports. Each must be allowed in the library's layer (rule 1), and a public name sits in exactly one cell. "geo" marks Operators on carriers that live in a model's geo extra.
