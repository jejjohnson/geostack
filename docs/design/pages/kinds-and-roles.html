Three kinds of function, three kinds of data

How code in the stack is packaged (function, Module, Operator), what data it sees (array, named array, carrier), and the role each name plays in its library's API, from structures up to recipes. This page holds the problem, the objects in symbols, the role ladder, who works where, one vocabulary per axis, and the rules that follow. The layer map keeps the layers, the imports and the boundaries of each library, and links here.

The problem: why geo code is hard to write well

Take one running example: a methane plume in an EMIT hyperspectral scene over an oil and gas field. A matched filter turns the radiance into a methane enhancement, the plume is masked, and its emission rate comes from the mass of methane in the plume and the wind. Every step of it can go wrong in a way that raises no error.

ProblemWhat goes wrong, silentlyWhat fixes it
Axes by positionEMIT's radiance file stores (downtrack, crosstrack, band), which is (y, x, band); geoarray and most operators expect (band, y, x). mean(axis=0), meant as the scene's mean spectrum, averages down the rows instead and returns an array of a plausible size.named array: dims by name, mean(("y", "x"))
Lost georeferenceThe radiance comes in sensor geometry, with its geolocation in a separate lookup table. Orthorectify it by hand, or crop the bare array, np.asarray(scene)[..., 100:164, 100:164], and the transform no longer matches the pixels: the crop claims to start at the scene's corner, and the plume is attributed to a facility kilometres away.carrier: slicing and cropping move the transform with the data
Mismatched gridsThe wind for the emission rate comes from ERA5 on a 0.25° grid, the enhancement on a 60 m UTM grid. Index the wind array with the plume's pixel indices and you read the wind somewhere else on Earth, with no error as long as the indices fit.carrier: require_grid_match refuses; values on another grid are read at coordinates (interp_at)
NodataA radiance fill of -9999 enters the background mean and covariance as if it were data, and biases the filter over the whole scene, not only where it sits.carrier: fill_value and valid_mask
Maths locked in a containerThe matched filter written against xarray can't run on a GeoArray, and neither can be jitted: a CRS is not something JAX can trace. Each container gets its own copy of the algorithm.function and Module on plain arrays; the container is unwrapped outside them
Setup that can't be tracedThe background statistics (a mean, a shrunk covariance from scikit-learn, a solve with it) are refitted on every call, or forced under jit where they fail.Module: fit once at fit, call jittably after
Pipelines held together by scriptsThe chain from radiance to emission rate lives in one notebook; its settings (spectral window, threshold, wind source) can't be saved, swept or rerun exactly.Operator: config round-trip, |, Graph

The fixes split cleanly. The first four problems are about the data; the last three are about how the code is packaged. That is why the stack has two axes.

The objects, in symbols

The whole stack rests on two ideas: a function of arrays, 𝐲=f(𝐱,𝐮;𝜽)\vect{y} = f(\vect{x}, \vect{u}; \gvect{\theta}), and an Operator that lifts that function onto geographic data, h[f,𝜽](𝐱geo;α)h[f, \gvect{\theta}](\vect{x}_\text{geo}; \alpha). Everything else is bookkeeping about what the data knows and where the settings live. The symbols, each defined in full with its shape in the sections below:

  • 𝐱\vect{x}: the data as a plain array of numbers; 𝐲\vect{y}: the array the function returns.
  • 𝐮\vect{u}: what the function needs to know about where the data sits, as plain arrays or numbers: pixel areas, a transform, the air-mass factor of the sun and view angles, the methane absorption at each band's wavelength. It is read off the data, never fitted.
  • 𝜽∈ℝDθ\gvect{\theta} \in \mathbb{R}^{D_\theta}: the function's parameters, set when the Operator is built and constant over a call (a matched filter's background statistics when they are given, the wind speed of an emission estimate).
  • ff: the function itself, which sees only 𝐱\vect{x}, 𝐮\vect{u} and 𝜽\gvect{\theta}.
  • 𝐱geo\vect{x}_\text{geo}: the same data as a carrier, the array together with its axis names, coordinates and georeference.
  • α\alpha: the Operator's config, names and settings only (which bands, which spectral window, the units, the fill policy), so it round-trips through JSON.
  • h[f,𝜽]h[f, \gvect{\theta}]: the Operator built from ff and 𝜽\gvect{\theta}; called on a carrier with config α\alpha, it unwraps, calls ff, and rewraps. Written h[f]h[f] when 𝜽\gvect{\theta} is empty.

Two axes follow from those ideas: what the data knows (𝐱\vect{x} or 𝐱geo\vect{x}_\text{geo}), and how the code is packaged (ff, a Module, or h[f,𝜽]h[f, \gvect{\theta}]).

The running example is an orthorectified EMIT scene over an oil and gas field in the Permian Basin: Nband=285N_\text{band} = 285 bands from 381 to 2493 nm, and Nrow×NcolN_\text{row} \times N_\text{col} pixels of 60 m on a UTM grid. A matched filter turns its radiance into a methane enhancement in ppm m; a threshold and connected components mask the plume; the integrated mass enhancement and an ERA5 wind give the emission rate. Its dimension names follow geoarray, ("band", "y", "x"); the sizes are written NrowN_\text{row} and NcolN_\text{col} so that 𝐲\vect{y} stays the output of a function.

The data axis: what 𝐱\vect{x} knows

▦ Plain array

A block of numbers with a shape and nothing else:

𝐱∈ℝN1×…×NNax\vect{x} \in \mathbb{R}^{N_1 \times \ldots \times N_{N_\text{ax}}}
  • NaxN_\text{ax}: the number of axes; a=1,…,Naxa = 1, \ldots, N_\text{ax} indexes them.
  • NaN_a: the length of axis aa.

Example The scene is 𝐱∈ℝNband×Nrow×Ncol\vect{x} \in \mathbb{R}^{N_\text{band} \times N_\text{row} \times N_\text{col}}, so Nax=3N_\text{ax} = 3. Which axis is the band is a convention the code has to remember. EMIT's radiance file stores (y, x, band) and geoarray (band, y, x); a mean over axis 0 meant as the mean spectrum averages down the rows instead, and runs without an error.

In code a NumPy or JAX array. Its axis order lives in a jaxtyping annotation and in each einx pattern, so the convention is written down at every call, but nothing checks it against the data: a scene read as (y, x, band) passes the same call and averages over the wrong axes.

import einx
import jax.numpy as jnp
import numpy as np
from jaxtyping import Array, Float


def mean_spectrum(radiance: Float[Array, "band y x"]) -> Float[Array, " band"]:
    """Mean radiance spectrum of a scene.

    x̄ = (1 / N_row N_col) ∑_ij x_ij
    """
    # the axis names live in this pattern and the annotation, not in the data
    spectrum = einx.mean("band [y x]", radiance)
    return spectrum


# x ∈ ℝ^(N_band × N_row × N_col): a 256 × 256 crop of an EMIT scene, on the host
radiance = np.zeros((285, 256, 256), dtype=np.float32)
# the same numbers on the device
scene = jnp.asarray(radiance)
spectrum = mean_spectrum(scene)

▤ Named array

The same numbers with a name dad_a and a coordinate vector 𝐜a\vect{c}_a for each axis:

𝐱named=(𝐱,𝐝,𝒞)\vect{x}_\text{named} = (\vect{x}, \vect{d}, \mathcal{C})
𝐝=(d1,…,dNax)\vect{d} = (d_1, \ldots, d_{N_\text{ax}})
𝒞=(𝐜1,…,𝐜Nax)\mathcal{C} = (\vect{c}_1, \ldots, \vect{c}_{N_\text{ax}})
  • 𝐝\vect{d}: one name per axis, all distinct.
  • 𝐜a∈ℝNa\vect{c}_a \in \mathbb{R}^{N_a}: the coordinates along axis aa (wavelengths, positions, dates).

An operation addresses an axis by name, and the array finds its position. Take a reduction rar_a (a mean, a sum, a maximum) over axis aa of a plain array: it maps ℝN1×…×NNax\mathbb{R}^{N_1 \times \ldots \times N_{N_\text{ax}}} to the same space with the factor NaN_a left out. On a named array the same reduction is asked for by a name dd. The array looks up its position, a=pos𝐝(d)a = \op{pos}_{\vect{d}}(d), reduces there, and removes that axis's name and coordinates, since the output no longer has that axis:

rd(𝐱named)=(ra(𝐱),𝐝−a,𝒞−a)r_d(\vect{x}_\text{named}) = (r_a(\vect{x}), \vect{d}_{-a}, \mathcal{C}_{-a})
𝐝−a=(d1,…,da−1,da+1,…,dNax)\vect{d}_{-a} = (d_1, \ldots, d_{a-1}, d_{a+1}, \ldots, d_{N_\text{ax}})
𝒞−a=(𝐜1,…,𝐜a−1,𝐜a+1,…,𝐜Nax)\mathcal{C}_{-a} = (\vect{c}_1, \ldots, \vect{c}_{a-1}, \vect{c}_{a+1}, \ldots, \vect{c}_{N_\text{ax}})
  • pos𝐝(d)\op{pos}_{\vect{d}}(d): the position of the name dd in 𝐝\vect{d}; an error if dd is not there.
  • 𝐝−a\vect{d}_{-a}, 𝒞−a\mathcal{C}_{-a}: the names and coordinates with entry aa taken out.

Example 𝐝=(𝚋𝚊𝚗𝚍,𝚢,𝚡)\vect{d} = (\texttt{band}, \texttt{y}, \texttt{x}), with 𝐜1\vect{c}_1 the band wavelengths. The mean spectrum reduces by name twice, over 𝚢\texttt{y} at pos𝐝(𝚢)=2\op{pos}_{\vect{d}}(\texttt{y}) = 2 and then over 𝚡\texttt{x}, and returns names (𝚋𝚊𝚗𝚍)(\texttt{band}) with the wavelengths still attached, whatever order the reader used.

In code pipekit-array's DimArray: the data, one name per axis, and static labels on the dims that have them (here the wavelengths), with no other coordinates. It is a JAX pytree whose only leaf is the data, so new values never recompile. An xarray DataArray is the same object with full coordinates, and pipekit's dim functions (reduce, sel, isel, transpose) run on both through their adapters.

import einx
import numpy as np
import pipekit_array as pa

radiance = np.zeros((285, 256, 256), dtype=np.float32)

WAVELENGTHS_NM = tuple(np.linspace(381.0, 2493.0, 285).round(1).tolist())

# x_named = (x, d, C): one name per axis, the band dim labelled by wavelength
scene = pa.DimArray(radiance, ("band", "y", "x"), {"band": WAVELENGTHS_NM})
# r over y, then x: the mean spectrum, found by name
spectrum = pa.reduce(scene, "mean", ("y", "x"))
# the file's own order, (y, x, band): the same call gives the same answer
as_stored = einx.id("band y x -> y x band", radiance)
stored = pa.DimArray(as_stored, ("y", "x", "band"), {"band": WAVELENGTHS_NM})
same_spectrum = pa.reduce(stored, "mean", ("y", "x"))

◆ Carrier

A named array plus its georeference Γ\Gamma:

𝐱geo=(𝐱named,Γ)\vect{x}_\text{geo} = (\vect{x}_\text{named}, \Gamma)
Γ=(crs,𝐀,xfill,ℳ)\Gamma = (\op{crs}, \mat{A}, x_\text{fill}, \mathcal{M})
  • crs\op{crs}: the coordinate reference system (an EPSG code or WKT).
  • 𝐀∈ℝ2×3\mat{A} \in \mathbb{R}^{2 \times 3}: the affine transform from pixel to map coordinates.
  • xfill∈ℝx_\text{fill} \in \mathbb{R}: the fill value, NaN allowed.
  • ℳ\mathcal{M}: the attributes (units, sensor, the sun and view zenith angles, processing level). Band names and wavelengths are coordinates of the band axis, in 𝒞\mathcal{C}.

The transform says where each pixel is. The top-left corner of the pixel in row ii and column jj sits at map coordinates 𝐬ij∈ℝ2\vect{s}_{ij} \in \mathbb{R}^2, and its centre at (j+1/2,i+1/2)(j + 1/2, i + 1/2) in pixel units:

𝐬ij=𝐀(ji1)\vect{s}_{ij} = \mat{A} \begin{pmatrix} j \\ i \\ 1 \end{pmatrix}

The fill value says which pixels are missing. A pixel is valid when every band there is finite and differs from the fill, which gives the valid mask 𝐦∈{0,1}Nrow×Ncol\vect{m} \in \{0, 1\}^{N_\text{row} \times N_\text{col}}, with bb indexing bands:

[𝐦]ij=∏b=1Nband𝟏[xb,i,j≠xfill]𝟏[xb,i,j is finite][\vect{m}]_{ij} = \prod_{b=1}^{N_\text{band}} \mathbf{1}[x_{b,i,j} \neq x_\text{fill}] \mathbf{1}[x_{b,i,j} \text{ is finite}]

For a swath or a curvilinear grid, as EMIT's radiance is before orthorectification, 𝐀\mat{A} is replaced by per-pixel coordinates 𝐒lon,𝐒lat∈ℝNrow×Ncol\mat{S}_\text{lon}, \mat{S}_\text{lat} \in \mathbb{R}^{N_\text{row} \times N_\text{col}}; the rest is the same.

Example The scene is a carrier on a 60 m grid in UTM zone 13N with xfill=−9999x_\text{fill} = -9999, the band names and centre wavelengths in 𝒞\mathcal{C}, and the sun and view zenith angles in ℳ\mathcal{M}. The well pad at map coordinates 𝐬\vect{s} is found at pixel (i,j)(i, j) by solving 𝐬=𝐀(j,i,1)⊤\vect{s} = \mat{A} (j, i, 1)^\top for (i,j)(i, j), which is to_pixel. Slice the bare array instead, np.asarray(scene)[..., 100:164, 100:164], and 𝐀\mat{A} still describes the full scene: the window claims to start at the scene's corner, and the plume is attributed to a facility several kilometres away.

In code geotoolz-array's GeoArray: the data (NumPy or JAX), its dims ending in ("y", "x"), coordinates for the other dims (SpectralAxis, TimeAxis), the transform, CRS, fill value and frozen attrs. Slicing, crop and read_window move the transform with the pixels; a reduction over y and x leaves no grid, so it returns a named array. GeoSwath carries per-pixel latitude and longitude instead of a transform, and GeoPoints a set of points; xrops plays the same role for a DataArray whose coordinates and CRS mean geography.

import numpy as np
import pipekit_array as pa
from geoarray import GeoArray, crop, to_pixel
from geoarray.coords import SpectralAxis

radiance = np.zeros((285, 256, 256), dtype=np.float32)

WAVELENGTHS_NM = tuple(np.linspace(381.0, 2493.0, 285).round(1).tolist())

BAND_NAMES = tuple(f"{wavelength:.1f}nm" for wavelength in WAVELENGTHS_NM)

# C: the band names with their centre wavelengths
bands = SpectralAxis(names=BAND_NAMES, wavelength_nm=WAVELENGTHS_NM)
# x_geo = (x_named, Γ), Γ = (crs, A, x_fill, M): a 60 m grid in UTM zone 13N
scene = GeoArray(
    radiance,
    (60.0, 0.0, 630000.0, 0.0, -60.0, 3550000.0),
    "EPSG:32613",
    fill_value=-9999.0,
    dims="band y x",
    coords=(bands,),
    attrs={"solar_zenith_deg": 28.4, "view_zenith_deg": 6.1},
)
# m: valid where every band is finite and differs from the fill
valid = scene.valid_mask()
# s = A (j + ½, i + ½, 1)ᵀ, solved for the fractional (i, j) of the well pad
well_pad_xy = np.array([[637530.0, 3542210.0]])
well_pad_pixel = to_pixel(scene.transform, well_pad_xy)
# a 64 × 64 window from row 100, column 100 moves A with the pixels
window = crop(scene, (100, 100), (64, 64))
# with y and x reduced there is no grid left: a named array, not a carrier
spectrum = pa.reduce(scene, "mean", ("y", "x"))

The kind axis: how ff is packaged

ƒ Function

A pure function of arrays, with its parameters passed in on every call:

𝐲=f(𝐱,𝐮;𝜽)\vect{y} = f(\vect{x}, \vect{u}; \gvect{\theta})
  • 𝐱\vect{x}: the input array; 𝐲\vect{y}: the output array.
  • 𝐮\vect{u}: what ff needs to know about where the data sits, as plain arrays or numbers (pixel areas, a transform, an air-mass factor, absorption at the band wavelengths).
  • 𝜽∈ℝDθ\gvect{\theta} \in \mathbb{R}^{D_\theta}: parameters, constant over the call.

ff never sees a name, a CRS or a fill value. That is what lets it run under jit, on any carrier, in any library below GeoStack.

Example The matched filter, the first step of the running example. With n=1,…,NrowNcoln = 1, \ldots, N_\text{row} N_\text{col} indexing pixels and 𝐱n∈ℝNband\vect{x}_n \in \mathbb{R}^{N_\text{band}} the spectrum at pixel nn, it estimates the methane enhancement yny_n, in ppm m, that best explains how 𝐱n\vect{x}_n departs from the background. Here the background is given, as the parameters 𝜽=(𝝁,𝚺)\gvect{\theta} = (\gvect{\mu}, \gmat{\Sigma}):

yn=𝐭⊤𝚺−1(𝐱n−𝝁)𝐭⊤𝚺−1𝐭y_n = \frac{\vect{t}^\top \gmat{\Sigma}^{-1} (\vect{x}_n - \gvect{\mu})}{\vect{t}^\top \gmat{\Sigma}^{-1} \vect{t}}

The target signature 𝐭\vect{t} is the radiance change for one ppm m of methane. Linearising the Beer–Lambert law, xn,b≈μb(1−Mkbyn)x_{n,b} \approx \mu_b (1 - M k_b y_n) for band bb, gives

𝐭=−M(𝐤⊙𝝁)\vect{t} = -M (\vect{k} \odot \gvect{\mu})
  • 𝝁∈ℝNband\gvect{\mu} \in \mathbb{R}^{N_\text{band}}, 𝚺∈ℝNband×Nband\gmat{\Sigma} \in \mathbb{R}^{N_\text{band} \times N_\text{band}}: the background mean and covariance.
  • 𝐤∈ℝNband\vect{k} \in \mathbb{R}^{N_\text{band}}: the methane absorption at each band's wavelength, per ppm m along a vertical path.
  • M∈ℝM \in \mathbb{R}: the geometric air-mass factor, one over the cosine of the solar zenith angle plus one over the cosine of the view zenith angle.
  • 𝐮=(M,𝐤)\vect{u} = (M, \vect{k}): both read off the data, the angles from the attributes and the absorption at the band coordinate's wavelengths.
  • 𝐭∈ℝNband\vect{t} \in \mathbb{R}^{N_\text{band}}: the target signature; ⊙\odot multiplies element by element.

The output keeps a singleton band axis, 𝐲∈ℝ1×Nrow×Ncol\vect{y} \in \mathbb{R}^{1 \times N_\text{row} \times N_\text{col}}.

import einx
import lineax as lx
from jaxtyping import Array, Float


def matched_filter(
    radiance: Float[Array, "band y x"],
    unit_absorption: Float[Array, " band"],
    air_mass: float,
    *,
    mean: Float[Array, " band"],
    covariance: lx.AbstractLinearOperator,
) -> Float[Array, "1 y x"]:
    """Methane enhancement of every pixel, by a matched filter.

    y_n = tᵀ Σ⁻¹ (x_n − μ) / (tᵀ Σ⁻¹ t),  t = −M (k ⊙ μ)
    """
    # t = −M (k ⊙ μ): the radiance change for 1 ppm m of methane
    target = -air_mass * unit_absorption * mean
    # s = Σ⁻¹ t
    solution = lx.linear_solve(covariance, target)
    filter_direction = solution.value
    # tᵀ Σ⁻¹ t
    normalisation = einx.dot("band, band ->", target, filter_direction)
    # r_n = x_n − μ
    residual = einx.subtract("band y x, band -> band y x", radiance, mean)
    # sᵀ r_n
    projection = einx.dot("band y x, band -> y x", residual, filter_direction)
    # y_n = sᵀ r_n / (tᵀ s), keeping a singleton band axis
    enhancement = projection / normalisation
    return einx.id("y x -> 1 y x", enhancement)

▣ Module

A function with state. A setup step builds the state 𝝍\gvect{\psi} once, from data 𝐗\mat{X} and what it needs to know about them, 𝐮\vect{u}, and may do work that cannot be traced (a scikit-learn estimator, a k-NN graph, a factorisation). The call is then pure and jittable:

𝝍=setup(𝐗,𝐮;𝜽)\gvect{\psi} = \op{setup}(\mat{X}, \vect{u}; \gvect{\theta})
𝐲=f(𝐱,𝐮;𝜽,𝝍)\vect{y} = f(\vect{x}, \vect{u}; \gvect{\theta}, \gvect{\psi})
  • 𝐗\mat{X}: the data setup sees, one row per sample; for the matched filter, the spectra of the valid pixels, 𝐗∈ℝNvalid×Nband\mat{X} \in \mathbb{R}^{N_\text{valid} \times N_\text{band}}.
  • 𝝍\gvect{\psi}: the state, a pytree of arrays held as the Module's fields next to 𝜽\gvect{\theta}.

Example The matched filter as it is used: the plume covers a small fraction of the pixels, so the scene is its own background. Setup estimates 𝝁\gvect{\mu} and a shrunk 𝚺\gmat{\Sigma} from 𝐗\mat{X} (Ledoit–Wolf, in scikit-learn), forms 𝐭\vect{t}, and solves once for the filter direction 𝐬=𝚺−1𝐭\vect{s} = \gmat{\Sigma}^{-1} \vect{t}; the state is 𝝍=(𝝁,𝐬,𝐭⊤𝐬)\gvect{\psi} = (\gvect{\mu}, \vect{s}, \vect{t}^\top \vect{s}). Each call is then two contractions:

yn=𝐬⊤(𝐱n−𝝁)𝐭⊤𝐬y_n = \frac{\vect{s}^\top (\vect{x}_n - \gvect{\mu})}{\vect{t}^\top \vect{s}}
import einx
import equinox as eqx
import jax.numpy as jnp
import numpy as np
import scipy.linalg
import sklearn.covariance
from jaxtyping import Array, Float


class MatchedFilter(eqx.Module):
    """Matched filter whose background is fitted once, from the scene's own pixels.

    y_n = sᵀ (x_n − μ) / (tᵀ s),  s = Σ⁻¹ t, with μ, Σ and s fixed at setup
    """

    mean: Float[Array, " band"]
    filter_direction: Float[Array, " band"]
    normalisation: Float[Array, ""]

    @classmethod
    def fit(
        cls,
        spectra: Float[np.ndarray, "pixel band"],
        unit_absorption: Float[np.ndarray, " band"],
        air_mass: float,
    ) -> "MatchedFilter":
        # --- setup: host-side NumPy, SciPy and scikit-learn, runs once ---
        # μ, Σ: the background mean and a Ledoit–Wolf shrunk covariance
        background = sklearn.covariance.LedoitWolf().fit(spectra)
        mean = background.location_
        # t = −M (k ⊙ μ)
        target = -air_mass * unit_absorption * mean
        # s = Σ⁻¹ t, solved once
        filter_direction = scipy.linalg.solve(
            background.covariance_, target, assume_a="pos"
        )
        # tᵀ s
        normalisation = einx.dot("band, band ->", target, filter_direction)
        return cls(
            mean=jnp.asarray(mean),
            filter_direction=jnp.asarray(filter_direction),
            normalisation=jnp.asarray(normalisation),
        )

    def __call__(self, radiance: Float[Array, "band y x"]) -> Float[Array, "1 y x"]:
        # --- every call: two contractions, pure and jittable ---
        # r_n = x_n − μ
        residual = einx.subtract("band y x, band -> band y x", radiance, self.mean)
        # sᵀ r_n
        projection = einx.dot(
            "band y x, band -> y x", residual, self.filter_direction
        )
        # y_n = sᵀ r_n / (tᵀ s)
        enhancement = projection / self.normalisation
        return einx.id("y x -> 1 y x", enhancement)

→ Operator

A pipeline step that lifts ff onto carriers. The Operator h[f,𝜽]h[f, \gvect{\theta}] is built from the function and its parameters; it is called on a carrier with its config α\alpha, a JSON record (which bands, which dimension, the fill policy). It unwraps the carrier with πα\pi_\alpha, calls ff on plain arrays, and rewraps with ια\iota_\alpha:

h[f,𝜽](𝐱geo;α)=ια(f(πα(𝐱geo);𝜽),𝐱geo)h[f, \gvect{\theta}](\vect{x}_\text{geo}; \alpha) = \iota_\alpha(f(\pi_\alpha(\vect{x}_\text{geo}); \gvect{\theta}), \vect{x}_\text{geo})
πα(𝐱geo)=(𝐱,𝐮)\pi_\alpha(\vect{x}_\text{geo}) = (\vect{x}, \vect{u})

Read the first line from the inside out: πα\pi_\alpha unwraps, ff computes, ια\iota_\alpha rewraps. The unwrap hands down the array and what ff needs to know about it, 𝐮\vect{u}, with every name in α\alpha already resolved against the carrier's names and coordinates. 𝜽\gvect{\theta} passes through untouched; α\alpha never reaches ff. The rewrap builds the output carrier:

ια(𝐲,𝐱geo)=𝐲geo=((𝐲,𝐝y,𝒞y),Γy)\iota_\alpha(\vect{y}, \vect{x}_\text{geo}) = \vect{y}_\text{geo} = ((\vect{y}, \vect{d}_y, \mathcal{C}_y), \Gamma_y)
Γy={Γsame gridregridα(Γ)new grid\Gamma_y = \begin{cases} \Gamma & \text{same grid} \\ \op{regrid}_\alpha(\Gamma) & \text{new grid} \end{cases}
  • α\alpha: the config, names and settings only, so it round-trips through JSON.
  • πα\pi_\alpha, ια\iota_\alpha: the unwrap and the rewrap, both read α\alpha; ια\iota_\alpha also takes the input carrier, whose georeference the output inherits or regrids.
  • 𝐝y\vect{d}_y, 𝒞y\mathcal{C}_y, Γy\Gamma_y: the output's names, coordinates and georeference.
  • regridα\op{regrid}_\alpha: the input grid to the output grid, for a reprojection or a resampling.

Operators compose: h[f2,𝜽2](h[f1,𝜽1](𝐱geo;α1);α2)h[f_2, \gvect{\theta}_2](h[f_1, \gvect{\theta}_1](\vect{x}_\text{geo}; \alpha_1); \alpha_2) is what pipekit writes step1 | step2, each step holding its own 𝜽\gvect{\theta} and α\alpha.

Example The settings are the band dim and a spectral window, α={dim:𝚋𝚊𝚗𝚍,window:[2122,2488] nm}\alpha = \{\text{dim}: \texttt{band}, \text{window}: [2122, 2488] \text{ nm}\}. πα\pi_\alpha resolves them against the carrier: it keeps the bands whose wavelengths in 𝒞\mathcal{C} fall in the window, computes 𝐮=(M,𝐤)\vect{u} = (M, \vect{k}) from the angles in ℳ\mathcal{M} and those wavelengths, and stacks 𝐗\mat{X} from the pixels where [𝐦]ij=1[\vect{m}]_{ij} = 1. The Module's setup runs on 𝐗\mat{X}, its call on the window. ια\iota_\alpha returns a carrier on the same grid, Γy=Γ\Gamma_y = \Gamma, with one band named ch4 and NaN where [𝐦]ij=0[\vect{m}]_{ij} = 0. geoops ships this step as geoops.matched_filter.MatchedFilter, which fits its background on the first call.

import einx
import numpy as np
import pipekit
from geoarray import GeoArray
from geoops.carrier import wrap_like
from radtrax.atmosphere import air_mass_factor

# MatchedFilter is the Module above; ch4_unit_absorption stands for a lookup of
# methane absorption per ppm m at given wavelengths, in radtrax


class MethaneEnhancement(pipekit.Operator):
    """CH₄ enhancement on a carrier: unwrap, fit the filter, filter, rewrap."""

    def __init__(
        self, *, dim: str = "band", window_nm: tuple[float, float] = (2122.0, 2488.0)
    ) -> None:
        # α: names and settings only, so the config round-trips through JSON
        self.dim = dim
        self.window_nm = window_nm

    def _apply(self, scene: GeoArray["band y x"]) -> GeoArray["1 y x"]:
        # --- π_α: the names in α, resolved against C and M ---
        # the bands inside the SWIR window, by wavelength
        bands = scene.coord(self.dim)
        lower, upper = self.window_nm
        window = [
            name
            for name, wavelength in zip(bands.names, bands.wavelength_nm)
            if lower <= wavelength <= upper
        ]
        swir = scene.sel({self.dim: window})
        # u = (M, k): M from the angles in the attrs, k at the window's wavelengths
        air_mass = air_mass_factor(
            swir.attrs["solar_zenith_deg"], swir.attrs["view_zenith_deg"]
        )
        unit_absorption = ch4_unit_absorption(swir.coord(self.dim).wavelength_nm)
        # X: the spectra of the valid pixels, one row each
        valid = swir.valid_mask()
        pixels = einx.id("band y x -> (y x) band", np.asarray(swir))
        is_valid = einx.id("y x -> (y x)", valid)
        spectra = pixels[is_valid]
        # --- the Module: setup once, then a pure call on plain arrays ---
        matched_filter = MatchedFilter.fit(spectra, unit_absorption, air_mass)
        enhancement = np.asarray(matched_filter(swir.data))
        # --- ι_α: same grid, one band in ppm m, NaN where m = 0 ---
        enhancement = np.where(valid, enhancement, np.nan)
        return wrap_like(swir, enhancement, band_names=("ch4",), fill_value=np.nan)

The sketches follow the house style: shapes as jaxtyping types, the equation above each line, einx for reshapes and contractions. All six run as written (checked on 6 Nov 2026): the data-axis examples against geotoolz-array and pipekit-array, and the function, the Module and the Operator on a synthetic scene with lineax and scikit-learn. In the Operator, air_mass_factor is radtrax's (radtrax.atmosphere) and ch4_unit_absorption stands for a lookup table of methane absorption (radtrax, or plumax's hapi_lut); geoops ships the matching Operators, matched_filter.MatchedFilter, plume.PlumeMask, plume.ColumnToMass and plume.IMEEstimate.

Parallels: operator learning, Lift & Learn and Koopman

The shape of an Operator, down, compute, up, is not new: neural operators and lifted reduced models use it too. Open for how they line up, and where they differ.

Operator learning. A neural operator learns a map 𝒢\mathcal{G} between function spaces, from an input field x(𝐬)x(\vect{s}) to an output field y(𝐬)y(\vect{s}), with 𝐬∈Ω\vect{s} \in \Omega the coordinates of the domain. Every architecture in the family factors into an encoder, an approximator and a reconstructor (Lanthaler, Mishra and Karniadakis, 2022; Kovachki, Lanthaler and Stuart, 2024):

𝒢≈ℛ∘𝒜∘ℰ\mathcal{G} \approx \mathcal{R} \circ \mathcal{A} \circ \mathcal{E}
  • ℰ\mathcal{E}: the encoder, from a field to a vector, its values at sensors or on a grid.
  • 𝒜\mathcal{A}: the approximator, from vector to vector: the network.
  • ℛ\mathcal{R}: the reconstructor, from the output vector back to a field.

DeepONet's sensor values are ℰ\mathcal{E}, its branch net 𝒜\mathcal{A} and its trunk net the basis of ℛ\mathcal{R} (Lu et al., 2021). The Fourier neural operator raises the channels with a map 𝒫\mathcal{P}, applies its kernel layers, and lowers them with 𝒬\mathcal{Q} (Li et al., 2021; Kovachki et al., 2023). A carrier is a discretised field, and its georeference Γ\Gamma says which discretisation, so πα\pi_\alpha plays ℰ\mathcal{E}, ff plays 𝒜\mathcal{A} and ια\iota_\alpha plays ℛ\mathcal{R}. Discretisation invariance, one operator for any grid, is the counterpart of an Operator that runs on any carrier whose names resolve.

Lift & Learn and Koopman. These change the state's variables to ones in which the dynamics are simpler, learn the simple model there, and map back. Take the state as a vector 𝐱∈ℝDx\vect{x} \in \mathbb{R}^{D_x}. Lift & Learn (Qian, Kramer, Peherstorfer and Willcox, 2020) picks a lifting 𝐰=𝒯(𝐱)\vect{w} = \mathcal{T}(\vect{x}) in which the dynamics are quadratic, and fits the two operators by least squares from snapshots, which is operator inference (Peherstorfer and Willcox, 2016):

d𝐰dt=𝐋1𝐰+𝐋2(𝐰⊗𝐰)\frac{\mathrm{d} \vect{w}}{\mathrm{d} t} = \mat{L}_1 \vect{w} + \mat{L}_2 (\vect{w} \otimes \vect{w})

Koopman's view (Koopman, 1931) lifts into a dictionary of observables 𝝓(𝐱)\gvect{\phi}(\vect{x}) in which the dynamics are linear; extended dynamic mode decomposition fits the finite Koopman matrix 𝐋\mat{L} from snapshot pairs (Williams, Kevrekidis and Rowley, 2015):

𝝓(𝐱t+1)≈𝐋𝝓(𝐱t)\gvect{\phi}(\vect{x}_{t+1}) \approx \mat{L} \gvect{\phi}(\vect{x}_t)
  • 𝒯:ℝDx→ℝDw\mathcal{T}: \mathbb{R}^{D_x} \to \mathbb{R}^{D_w}: the lifting; 𝐰∈ℝDw\vect{w} \in \mathbb{R}^{D_w}, the lifted state.
  • 𝐋1∈ℝDw×Dw\mat{L}_1 \in \mathbb{R}^{D_w \times D_w}, 𝐋2∈ℝDw×Dw2\mat{L}_2 \in \mathbb{R}^{D_w \times D_w^2}: the linear and quadratic operators.
  • 𝝓:ℝDx→ℝDϕ\gvect{\phi}: \mathbb{R}^{D_x} \to \mathbb{R}^{D_\phi}: the observables; 𝐋∈ℝDϕ×Dϕ\mat{L} \in \mathbb{R}^{D_\phi \times D_\phi}, the Koopman matrix.

What carries over, and what does not.

  • The same shape. A map down, a computation on plain vectors, a map up. In both literatures, and here, the point is that the middle is written once and reused under any encoder.
  • The opposite direction. There, lifting goes up: into more channels, or into coordinates where the model is linear or quadratic. Here πα\pi_\alpha goes down: it strips the names and the georeference and keeps the values as they are. That clash is one reason this page writes h[f,𝜽]h[f, \gvect{\theta}] rather than "lift".
  • A different job. Their lift changes the variables, so it is part of the model, designed or learned with it. Ours changes only the container: it is bookkeeping, and ff sees the same numbers either way.
  • They nest. A Lift & Learn or Koopman model is a Module: its setup fits 𝐋1,𝐋2\mat{L}_1, \mat{L}_2 or 𝐋\mat{L} from snapshots 𝐗\mat{X}, and its call applies the lifting, the learned map and the map back. A trained neural operator is a Module too. Wrapping either in hh puts it on carriers, with the unwrap and the rewrap of the carrier handled by πα\pi_\alpha and ια\iota_\alpha.

The running example, end to end

Four steps in one recipe, each a lifted function:

𝐲geo=h[fmf,𝝍](𝐱geo;α1)\vect{y}_\text{geo} = h[f_\text{mf}, \gvect{\psi}](\vect{x}_\text{geo}; \alpha_1)
𝐛geo=h[fmask](𝐲geo;α2)\vect{b}_\text{geo} = h[f_\text{mask}](\vect{y}_\text{geo}; \alpha_2)
U=h[fwind](𝐯geo;α3)U = h[f_\text{wind}](\vect{v}_\text{geo}; \alpha_3)
Q=h[fime,U](𝐲geo,𝐛geo;α4)Q = h[f_\text{ime}, U](\vect{y}_\text{geo}, \vect{b}_\text{geo}; \alpha_4)

Here 𝐲geo\vect{y}_\text{geo} is the methane enhancement in ppm m and 𝐛geo\vect{b}_\text{geo} the plume mask, both on the scene's grid; 𝐯geo\vect{v}_\text{geo} is ERA5's 10 m wind speed on its own 0.25° grid, read at the source's coordinates to give the wind UU in m s⁻¹; and QQ is the emission rate in kg h⁻¹. fmff_\text{mf} is the Module above, with 𝝍\gvect{\psi} fitted on the scene; fmaskf_\text{mask} thresholds and keeps connected components; fimef_\text{ime} is the integrated mass enhancement method:

Q=UL∑n=1NrowNcolbnκynanQ = \frac{U}{L} \sum_{n=1}^{N_\text{row} N_\text{col}} b_n \kappa y_n a_n

with bnb_n the mask at pixel nn, ana_n its area and LL the plume length, both from 𝐀\mat{A}, and κ\kappa the mass of methane per square metre in one ppm m. The last step takes UU as its parameter 𝜽\gvect{\theta}, and it is terminal: ια\iota_\alpha returns a table (QQ with its uncertainty), not a carrier. Only the four configs α1,…,α4\alpha_1, \ldots, \alpha_4 mention band names, windows, units, thresholds or the source's coordinates. In geoops the steps are MatchedFilter, PlumeMask, interp_at on the wind, and ColumnToMass followed by IMEEstimate.

Carriers stop at the GeoStack: nothing below sees 𝐱geo\vect{x}_\text{geo}, only πα(𝐱geo)=(𝐱,𝐮)\pi_\alpha(\vect{x}_\text{geo}) = (\vect{x}, \vect{u}). The data axis in three lines

▦ A plain array 𝐱\vect{x} knows its shape.

▤ A named array 𝐱named=(𝐱,𝐝,𝒞)\vect{x}_\text{named} = (\vect{x}, \vect{d}, \mathcal{C}) knows which axis is which.

◆ A carrier 𝐱geo=(𝐱named,Γ)\vect{x}_\text{geo} = (\vect{x}_\text{named}, \Gamma) also knows where each pixel is (𝐀\mat{A}), and which pixels are missing (xfillx_\text{fill}, 𝐦\vect{m}).

So a carrier is a named array plus its georeference. The named array still earns its place: it is the protocol that lets one Operator (Reduce(dim="time")) run on DimArray, DataArray and GeoArray through their adapters, and it is the end product for data with dims but no geography: a DA ensemble (member, time, state), a sweep, a posterior summary.

"Kicking a Module up a notch" is two separate steps. Wrapping it in an Operator adds composition: a config, |, graph mode. Moving it to carriers adds georeference: the CRS, the fill, the attrs. The steps are independent. JaxModelOp and a DA cycle take the first step without the second; geoarray's crop and read_window take the second without the first. geoops Operators take both.

Inside a library: the role ladder

gaussx draws its API as a ladder: primitives, operators, strategies, distributions, recipes. The same ladder fits every library in the stack, and it sits across the three kinds rather than beside them. Read it as grammar, from ⓪ down: structures are the nouns (Kronecker, and the data itself: arrays, named arrays, carriers), primitives the verbs that act on them (solve), strategies the adverbs that say how (CGSolver), models the noun phrases (a Gaussian with this mean), algorithms the sentences (kalman_filter), steps (pipekit Operators) a sentence with its own settings, ready to chain (MatchedFilter), and recipes the paragraphs: steps composed into one job, from source to product. Above the ladder, orchestration runs recipes; it is not a rung. Module is not a rung; it is how three rungs are packaged: ⓪ structures, ② strategies and ③ models. Its setup step setup\op{setup}, which builds state from data outside the jitted path, is what gaussx draws as the sidebar of tools that produce operators. Rungs are marked with circled digits, ⓪ to ⑥, so they cannot be confused with tiers (T) or processing levels (L); names in italics are proposed.

Why structures sit below primitives. In gaussx, _primitives imports _operators 76 times and _operators imports _primitives once: the verbs exist to dispatch on the nouns. With the nouns at the floor, the ladder is also the build order. One entanglement is left: a primitive takes a strategy argument (solve(A, b, solver=CGSolver())) and some strategies call primitives (diag, trace); _primitives and _strategies import each other eight times each way. That pair is gaussx's dispatch core, now its only documented exception.

The data are nouns too. ▦ arrays, ▤ named arrays and ◆ carriers are the ⓪ structures of the data axis: DimArray is pipekit-array's noun, GeoArray, GeoSwath and GeoPoints are geoarray's, and geoarray's own verbs (crop, to_pixel, read_window) are the ① primitives that act on them. The kind and data axes say how a noun is packaged and what it knows; the ladder says it is a noun.

Steps and recipes. The test between ⑤ and ⑥: does it do one thing to its input, or does it put steps (its own, or ones you pass in) in order to make a job? MatchedFilter and Reproject are steps; load, orthorectify, matched filter, plume mask and emission estimate, from an EMIT L1B scene to an emission rate, is a recipe. What counts is how it is built, not its name or what it does inside: Reproject resamples and warps internally but is one closed class with settings, so it is a step, and so is geoops.viz.RGBRecipe despite its name (RGBComposite would say it better). Some recipes ship in libraries as templates, compositions with slots for your steps: DACycle (forecast then analysis, cycled), TrainingLoop, and the patcher's split, process and stitch. The combinators (Sequential, Graph, Branch, Retry) are the conjunctions that join steps, so they sit at ⑥ too.

Composition is closed; running is not. A recipe of recipes is a recipe, as a Sequential of Sequentials is a Sequential, so the ladder stops at ⑥. What sits above is not more composition but running it: which items, when, where, with what retries and storage. That is orchestration, the application's job (a DVC stage, an Airflow or Prefect flow, a FastAPI endpoint, GeoApps), and the same recipe should run unchanged in all of them. A recipe has two forms, code (a Sequential or Graph built in Python) and data (a YAML file that pipekit.loads reads back). The data form needs every step in it to round-trip (a strict-JSON get_config, from_state, no live objects), and a recipe that comes from a user goes through loads_sandboxed with an allowlist: a recipe that names classes is code. Settings composed with Hydra override values inside a recipe; they do not become a second recipe format.

Against gaussx's own numbering: its L1 operators become ⓪ structures and its L0 primitives ① primitives (the swap above); L1.5, L2 and L3 become ② strategy, ③ model (its "distributions", renamed so the rung reads the same in libraries with none: a functax plan, a kernellib estimator, a sesmax model) and ④ algorithm; ⑤ step and ⑥ recipe are pipekit's. gaussx's word "recipes" moves up the ladder: in the stack a recipe is a composition of steps, as in a kitchen, in Pangeo Forge's ETL recipes and in torchtune's training recipes. UnscentedIntegrator moves from gaussx's recipes to the strategies: it is a choice of how to integrate, like CGSolver is a choice of how to solve.

Who works where: bands of the ladder

Each kind of user works in a band of the ladder and treats the rung below it as atomic: their floor. A geoscientist calls MatchedFilter and never opens it; an ML researcher calls solve and never opens it. The word is floor, not primitive: ① stays one role, the same for everyone.

Carriers start at ⑤, but ⑤ does not need carriers. Nothing below ⑤ computes on a carrier: that is the second of the three invariants under rule 3, nothing below GeoStack sees 𝐱geo\vect{x}_\text{geo}, only πα\pi_\alpha(𝐱geo\vect{x}_\text{geo}). A step is exactly where πα\pi_\alpha and ια\iota_\alpha happen, so geo territory begins there. The converse does not hold: JaxModelOp, a DA cycle and a training loop are steps and recipes on plain arrays. Geo territory is ⑤ and ⑥ with carrier data. geoarray's own nouns and verbs (GeoArray, crop, to_pixel) sit at ⓪ and ① but handle georeference only and compute no field. On the xarray side, geoscientists call functions on named arrays (xrops), so their floor is set by the data as much as by the rung.

Floors leak, so design for one rung down. When a step's settings fall short, a geoscientist should reach the algorithm it wraps without reading its source: every step's docstring names the function it calls (the ff in h[f,𝜽]h[f, \gvect{\theta}]). Errors speak the band's language: band names, CRS and fill at ⑤ and ⑥, shapes at ④ and below. Docs open by band, one entry point per kind of user, not one per library. And ⑤ and ⑥ are the API the most people touch, so they get the strictest deprecations.

Two names on every axis. gaussx.CGSolver: ② strategy · ▣ Module · ▦ array · Core T0. geoops.matched_filter.MatchedFilter: ⑤ step · → Operator · ◆ carrier · GeoStack T3; it turns an L1B radiance scene into an L2 enhancement product.

How the axes constrain each other. The role fixes the kind: ① and ④ are functions, ⓪, ② and ③ are Modules (or, at ⓪, a third-party array), ⑤ and ⑥ are Operators (a recipe in code is a Sequential or Graph, itself an Operator; in data, the YAML that loads into one), so a library's chips only need the digit. The kind and the data fix the lowest layer. Inside one library, imports follow the roles upward, nouns first; the one entanglement left is between verbs and adverbs (a primitive takes a strategy; some strategies call primitives), which gaussx documents as its dispatch core.

What this retires. The kind once called "primitive" is now "function", so "primitive" names one role (①) only. geostack's docs/design/stack_levels.md L1 to L3 (primitives and machinery, operators on carriers, pipelines) were a mix of kind and data; the glyph pairs say the same without a number (ƒ ▣ on ▦; → on ◆; ⑤ steps composed into ⑥ recipes). Two words stay where the field uses them on purpose: "linear operator" (lineax's AbstractLinearOperator, a ⓪ structure) and "observation operator" (H). Capital-O Operator means pipekit's kind only.

GeoNumerics fills only the plain-array column, and only its first two rows. Core adds Operators on plain arrays and, through pipekit-array, the named-array column. As a carrier, with a CRS, it belongs to xrops.

Which cell is it?

  1. Kind. Does it subclass pipekit.Operator? Then it is an Operator, whatever else it inherits; JaxOperator is also an eqx.Module and is still an Operator. Else, is it a class whose setup does work before a pure call? A Module. Else it is a function.
  2. Data. Does it take or return a CRS, a fill or attrs? Carrier. Dims with names and coordinates, but no CRS? Named array. Neither? Plain array.

Do we need a name change?

Not in code; in prose, yes. In code the namespaces already separate the two kinds of operator (lineax calls its own AbstractLinearOperator), and renaming pipekit.Operator would touch pipekit, every geoops and xrops class, vardax, plumax and sesmax, all for a prose problem. "Observation operator" is the field's own word for H and stays. In prose: function for the kind (not "kernel", which kernellib uses for covariance functions, nor "primitive", which now names the ① role), Module, Operator with a capital O for pipekit's, and carrier for the data. The full vocabulary, one per axis, is in the box under the role ladder. The suffix rules on the library cards of the layer map keep the class names apart as well.

Rule 2: the tier decides what a library may import

Unchanged: a library imports any lower layer, and lower tiers of its own layer. A tier never changes which kinds a library may define. pipekit and gaussx are both Core tier 0, yet one defines Operators and the other Modules; the cells come from the layer.

Three invariants

Arrays go everywhere. Every kind takes them.

Carriers stop at GeoStack. An Operator on carriers unwraps before it calls down and rewraps on the way back; nothing below GeoStack takes a carrier as input, and that includes xarray.DataArray. One narrow exception, listed by name with its reason:

An export at the edge. A method that only returns results as a labelled container (to_xarray), imports it lazily behind an extra, attaches no CRS, and is called by nothing else in the library. Carriers flowing out at the end couple nothing; carriers flowing in are what the rule stops.

Configs stop at Operators. Hydra and JSON configs build Operators and apps; Modules and functions take plain values (numbers, arrays, other Modules), never a DictConfig.

Rule 4: each library declares its cells

Every row of the boundaries table on the layer map carries the kinds and data that library exports. Each must be allowed in the library's layer (rule 1), and a public name sits in exactly one cell. "geo" marks Operators on carriers that live in a model's geo extra.

geoarray, gridax and functax: geometry has no CRS below GeoStack

geoarray stays a package of the geotoolz workspace and keeps every carrier. What moves out is the geometry maths it does today. Each geoarray grid becomes a CRS-free grid from below, with a pyproj.CRS attached. Affine raster grids are the CRS-free geometry functax already owns for interpolation; the grids that physics needs (curvilinear, swath, staggered, vertical) are gridax's; anything that knows the Earth's shape comes from geophysix.
