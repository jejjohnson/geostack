GeoStack · background · request → response

How does a request from outside become a product?

Pictures first. A backend is the part of a system other programs talk to. This page covers the conventions it speaks (HTTP and REST), the Python library most geo services are written in (FastAPI), the model-serving layer built on it (LitServe), and where each meets the stack. It builds one small service on the NDVI pipeline of the last page and measures it. One distinction runs through it: the catalogs we query are not the catalog we serve.

TL;DR

A thin, typed, forgetful layer over the pipeline

  • REST is a convention: things have addresses, a handful of verbs act on them, answers are JSON with a status code, and the server remembers nothing between requests.
  • Two STACs. Upstream, we are a client of other people's STAC APIs. Downstream, our pipeline writes a product database, which is mirrored into a product catalog that we serve as STAC to others.
  • FastAPI turns a typed Python function into an endpoint: it parses, validates, serialises and documents from the type hints.
  • Long work is a job. Accept the request, return an id at once (4 ms here), let the client check back. Make the id a hash of the request, so a retry cannot run it twice.
  • The blocking trap is real: one blocking call in an async endpoint turned 20 concurrent requests from 0.22 s into 4.03 s and held an unrelated health check for 4.0 s.
  • LitServe is FastAPI plus what model serving needs: load once, batch, spread over GPUs. It belongs at one endpoint, predict.

HTTP and REST

HTTP is the request-and-response exchange above. REST is a set of habits for using it: every thing the service knows about (a product, a job) is a resource with an address, and the HTTP verbs say what to do with it. You met the same verbs on the object storage page; a bucket is a REST service.

Two properties matter more than the rest. A service is stateless when each request carries everything needed to answer it. A request is idempotent when sending it twice has the same effect as sending it once. Both come back below.

Two STACs: the one we query and the one we serve

Why two stores downstream and not one? The product database is ours to shape: it changes with our pipelines and holds things no outside client needs. The product catalog is a promise to others: standard names, read-only, searchable by any STAC tool. Keeping the database as the source of truth and mirroring it outward means the public face can be rebuilt at any time and never has to be written by hand. In code, the product catalog design puts one interface over both, so publish does not care which it is talking to.

Which one am I talking to?
  • Looking for input scenes: an upstream STAC. You cannot write to it and should not mirror it wholesale; catalog only the hits.
  • Recording what a run made: the product database, through publish.
  • Letting someone else find our products: the product catalog, through our STAC API.
  • A later pipeline of ours looking for earlier products: either; the database if it needs our extra columns, the catalog if it should work like any other archive.

The demo's /products endpoint is the product database answered directly, with a small search of its own. It is not a STAC API; in production stac-fastapi provides that, with paging, filters and the standard item shape.

FastAPI: a typed function becomes an endpoint

The types are pydantic models: classes whose fields are declared with types and checked when an instance is built. They are the service's seams, in the sense of the pipeline page: a RunRequest is a GeoSlice that arrived as JSON; a Product is a product record on its way out.

class RunRequest(pydantic.BaseModel):
    """What a client sends to start a job: a site, a period and a recipe."""

    bounds: tuple[float, float, float, float]
    start: datetime.date
    end: datetime.date
    recipe: Literal["ndvi"] = "ndvi"


class Product(pydantic.BaseModel):
    """One row of our product database, as the API returns it."""

    id: str
    start_time: datetime.date
    end_time: datetime.date
    bbox: tuple[float, float, float, float]
    href: str
    snapshot_id: str
    recipe_hash: str


class Job(pydantic.BaseModel):
    """A run in progress or finished; product_id is set once it is done."""

    id: str
    status: Literal["queued", "running", "done", "failed"]
    product_id: str | None = None
@app.get("/products")
def search_products(
    bbox: str | None = None, start: datetime.date | None = None,
    end: datetime.date | None = None,
) -> list[Product]:
    """Our products that touch a box and a period: a query on our own table."""
    clauses, values = ["1 = 1"], []
    if bbox is not None:
        x0, y0, x1, y1 = (float(part) for part in bbox.split(","))
        clauses.append("x0 <= ? AND x1 >= ? AND y0 <= ? AND y1 >= ?")
        values += [x1, x0, y1, y0]
    if start is not None:
        clauses.append("end_time >= ?")
        values.append(str(start))
    if end is not None:
        clauses.append("start_time <= ?")
        values.append(str(end))
    query = f"SELECT * FROM products WHERE {' AND '.join(clauses)} ORDER BY id"
    with database() as db:
        return [product_from_row(row) for row in db.execute(query, values)]


@app.get("/products/{product_id}")
def get_product(product_id: str) -> Product:
    with database() as db:
        row = db.execute("SELECT * FROM products WHERE id = ?", (product_id,)).fetchone()
    if row is None:
        raise fastapi.HTTPException(status_code=404, detail="no such product")
    return product_from_row(row)

They differ in how long they take and what they wait on, so they should not share a design. Search and read answer inside the request. Run cannot. Predict needs hardware the others do not.

Long work is a job

@app.post("/jobs", status_code=202)
def start_job(
    request: RunRequest, http: fastapi.Request, response: fastapi.Response
) -> Job:
    """Accept a run and answer at once; the same request always gives the same job."""
    # job id = SHA-256(request ‖ recipe hash): a retry cannot start a second run
    payload = request.model_dump_json() + RECIPE_HASH
    job_id = hashlib.sha256(payload.encode()).hexdigest()[:12]
    with database() as db:
        row = db.execute("SELECT * FROM jobs WHERE id = ?", (job_id,)).fetchone()
        if row is not None:
            response.status_code = 200
            return job_from_row(row)
        db.execute("INSERT INTO jobs VALUES (?, 'queued', NULL)", (job_id,))
    http.app.state.workers.submit(run_recipe, job_id, request, http.app.state.catalog)
    return Job(id=job_id, status="queued")


@app.get("/jobs/{job_id}")
def get_job(job_id: str) -> Job:
    with database() as db:
        row = db.execute("SELECT * FROM jobs WHERE id = ?", (job_id,)).fetchone()
    if row is None:
        raise fastapi.HTTPException(status_code=404, detail="no such job")
    return job_from_row(row)

Three things make this safe. The response returns before the work starts, so no connection is held open. The job id is a hash of the request and the recipe, so the same request finds the existing job instead of starting another (the idempotency key). And the worker ends with commit and publish, so a finished job is an ordinary product record: nothing about the result lives in the web service.

When to make an endpoint a job
  • Answer in the request when the work is reliably under a second or two: search, a record, a small window.
  • Make it a job when it may take longer than a client or a proxy will wait (often 30 to 60 s), or when it must survive a dropped connection.
  • Let users send a recipe only as data, loaded through pipekit's loads_sandboxed with an allowlist: a recipe names classes, so a recipe from outside is code.

Polling is the simplest way to report progress. Webhooks, server-sent events and websockets push instead of being asked; they are refinements of the same idea.

The blocking trap, measured

def read_window() -> dict[str, float]:
    """Stand-in for a 200 ms blocking read (GDAL, NumPy, a database driver)."""
    time.sleep(0.2)
    return {"mean": 0.41}


@app.get("/read/blocking")
async def read_blocking() -> dict[str, float]:
    # async def + a blocking call: the event loop stops for every client
    return read_window()


@app.get("/read/plain")
def read_plain() -> dict[str, float]:
    # plain def: FastAPI runs it on a worker thread
    return read_window()


@app.get("/read/offloaded")
async def read_offloaded() -> dict[str, float]:
    # async def that hands the blocking call to a thread
    return await asyncio.to_thread(read_window)

FastAPI runs on an event loop (see parallelism). An async def endpoint runs on that loop, so anything in it that blocks stops every other request. A plain def endpoint is run on a worker thread for you, which is why it is the fastest here. The middle bar is slower only because asyncio.to_thread uses a smaller pool (6 threads on this 2-core machine) than the one FastAPI uses for plain functions (40 by default).

Which to write
  • Plain def when the body calls blocking libraries: GDAL, rasterio, NumPy, a synchronous database driver. This is most geo code.
  • async def when everything inside is awaited: an async HTTP client, obstore, an async database driver.
  • A worker process or a job when the body computes for long in Python or holds a lot of memory: threads share one interpreter.

geocloud already guards the other direction: its helper for running a coroutine from blocking code checks for a running loop, the situation a FastAPI handler is in.

Stateless services

LitServe: FastAPI for models

Serving a model has needs a plain endpoint does not: the weights must load once and stay loaded, requests that arrive together should run as one batch, and work should spread over the GPUs or processes available. LitServe, from Lightning AI, is a server built on FastAPI that provides those. You write a class with two required parts, setup (run once per worker) and predict (run per request or per batch), and it supplies the endpoint, the batching queue, the workers and streaming. Its own page reports at least twice the throughput of plain FastAPI on its benchmarks.

import litserve as ls

# not pinned (litserve)
class PlumeDetector(ls.LitAPI):
    def setup(self, device):
        # once per worker: load the weights onto the device
        self.model = load_model(device)

    def predict(self, request):
        # per request, or per batch when batching is on
        patch = decode(request["patch"])              # → (band, h, w)
        return {"mask": encode(self.model(patch))}    # → (h, w)

# not pinned (litserve)
server = ls.LitServer(PlumeDetector(max_batch_size=16), accelerator="auto")
server.run(port=8000)
When LitServe, and where in the stack
  • Use it for the predict kind of endpoint: a segmentation network, a retrieval emulator, anything on a GPU that benefits from batching.
  • In the pipeline it sits inside Apply: the patcher splits a field, each patch goes to the model server, the results are combined as usual.
  • Do not use it for search, read or run. None of them loads weights or batches, and each has a better-fitting tool.

The code above follows LitServe's published quick-start and was not run for this page; load_model, decode and encode are placeholders.
