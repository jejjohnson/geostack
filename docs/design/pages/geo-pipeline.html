GeoStack · background · question → product → question

What does every geoscience pipeline do, in order?

Pictures first. Whatever the science, the job has the same outline: find the scenes, read only what you need, cut it into pieces, compute, stitch, and keep the result so that someone can find it again. This page names ten stages for that outline, says what each hands to the next, and runs all ten on one small example. It starts from the eight-stage diagram in geotoolz and adds the two stages that versioned storage and a product catalog bring.

TL;DR

Find, compute, keep, and around again

  • Find: search an archive, catalog what it holds, save only the hits. No pixel is decoded in these three.
  • Compute: stream the hits as one lazy field, then split → apply → combine, which is xarray's pattern applied to space.
  • Keep: write the result, commit it as a version, publish a record of it. The last two are new.
  • Typed seams. Neighbouring stages hand over an object (a catalog, a field, a patch, a snapshot id), never a bare file path.
  • It is a loop. A published product is an archive: the next pipeline searches it. Each lap raises the processing level.
  • The test: all ten stages run on a 24-file archive; the patched NDVI matches the unpatched one to 2e-16, and the product reopened through its record's snapshot id is identical.

Ten stages, three acts

Act 1 · Find: from a question to a few files

Search asks an archive what it has. Catalog turns the answer into a table of footprints, times and paths, so the next question is a query on that table and not another crawl. Save brings only the matching files close to where the computing runs. The request itself is an object, a GeoSlice: bounds × time × resolution × CRS.

# Shapes: T = 2 bands; H × W = 400 × 500 px (the site); h × w = 128 × 128 px

# --- search ---
    # the archive: here a folder; in production a STAC, CMR or GEE search
    files = sorted(glob.glob(str(ARCHIVE / "*.tif")))             # → 24 paths

    # --- catalog ---
    # today (geocatalog)
    # index once: footprint, CRS, resolution and time per file; no pixels read
    catalog = build_raster_catalog(                               # 24 paths → 24 rows
        files, filename_regex=r"_(?P<date>\d{8})", date_format="%Y%m%d"
    )
    # today (geocatalog)
    # the request: bounds × time × resolution × CRS
    site = gc.GeoSlice(
        bounds=(723000.0, 4375000.0, 728000.0, 4379000.0),
        interval=pd.Interval(
            pd.Timestamp("2026-06-01"), pd.Timestamp("2026-06-30"), closed="both"
        ),
        resolution=(PIXEL_M, PIXEL_M),
        crs=CRS,
    )
    # today (geocatalog)
    hits = catalog.query(site)                                    # 24 rows → 6 rows

    # --- save ---
    # today (geocatalog)
    # fetch only the hits next to the compute; local files stay where they are
    staged = gc.staging.stage(hits, dest=str(WORK / "cache"))     # 6 rows → 6 rows
When a Find stage changes shape
  • Search is a STAC or CMR call in production; here it is a folder listing. Either way it returns names, not data.
  • Catalog can be skipped only for a one-off. A second question about the same archive is where it pays.
  • Save has nothing to do when the files are already next to the compute, as here. From a bucket it downloads the hits; with virtual references it records where the bytes are and copies nothing.

Background: databases and catalogs for the table and its indexes; object storage for why listing is slow and why only the hits are fetched.

Act 2 · Compute: split, apply, combine

Stream presents the saved files as one field: an array on the request's grid that reads pixels only when a window is asked for. Split cuts the field into overlapping patches. Apply runs one operator on each patch. Combine merges the results, weighting each patch so that the seams disappear.

# --- stream ---
    # today (geocatalog)
    # a Field: the six files as one lazy mosaic on the site's grid
    field = gc.patch.field_for(staged, site)                      # 6 rows → (T, H, W)

    # --- split ---
    # today (geopatcher)
    patcher = gp.SpatialPatcher(
        geometry=gp.spatial.geometry.Rectangular(size=(128, 128), boundary="pad"),
        sampler=gp.spatial.sampler.RegularStride(step=(96, 96)),
        window=gp.spatial.window.Hann(),
        aggregation=gp.spatial.aggregation.OverlapAdd(),
    )
    # today (geoops)
    patches = GridSampler(patcher=patcher)(field)                 # (T, H, W) → 20 × (T, h, w)

    # --- apply ---
    # today (geoops)
    # NDVI = (ρ_nir − ρ_red) / (ρ_nir + ρ_red)
    ndvi = gz.DNToReflectance(scale=1e-4) | gz.NDVI(red=0, nir=1)
    # today (geoops)
    results = ApplyToChips(operator=ndvi)(patches)                # 20 × (T, h, w) → 20 × (h, w)

    # --- combine ---
    # today (geoops)
    # window-weighted merge of the overlaps, back on the site's grid
    merge = MergePatches(
        aggregation=gp.spatial.aggregation.OverlapAdd(), domain=field.domain
    )
    product = merge(results)                                      # 20 × (h, w) → (H, W)
Why the merge has no seams (overlap-add)

Let patch \(p\) give a result \(y_p(n)\) at pixel \(n\), with a window weight \(w_p(n) \ge 0\) that is largest at the patch's centre and falls towards its edge (zero where the patch does not cover \(n\)). The merged value is the weighted mean over the patches that cover the pixel:

\[ \hat{y}(n) = \frac{\sum_p w_p(n) y_p(n)}{\sum_p w_p(n)} \]

For an operator that acts pixel by pixel, such as NDVI, every patch gives the same value at a shared pixel, so \(\hat{y}(n) = y(n)\) exactly; the measured difference is 2.2e-16. For an operator that looks at a neighbourhood (a convolution, a neural network), values near a patch edge are less reliable, and the weights are what keep them from showing.

When to split, and how much to overlap
  • Split when the field does not fit in memory, when patches should run at the same time, or when a model expects a fixed input size.
  • Overlap at least as far as the operator looks sideways: none for a per-pixel index, the receptive field for a network.
  • Do not split an operator that needs the whole scene at once (a scene-wide covariance): fit it first, then apply per patch.

Background: storage formats for how a window read fetches only its tiles; parallelism for running the patches at the same time.

Act 3 · Keep: a file, a version, a record

Write puts the result somewhere with its georeference intact. That is where the original eight stages end, and where two problems begin: a half-written result looks like a result, and nobody else knows it exists. Commit makes the write a version that appears all at once and can be named for ever. Publish adds one row to a product catalog saying what the product is, where it is, which version, and what made it.

# --- write ---
    # today (geoops)
    gz.WriteCOG(path=str(WORK / "ndvi_june.tif"))(product)        # (H, W) → 1 file

    # --- commit ---
    # today (icechunk)
    # the same product into a versioned store: visible all at once, or not at all
    repo = icechunk.Repository.create(
        icechunk.local_filesystem_storage(str(WORK / "products.icechunk"))
    )
    session = repo.writable_session("main")
    values = np.asarray(product)                                  # (H, W)
    array = zarr.create_array(
        session.store, name="ndvi", shape=values.shape, chunks=(256, 256), dtype="f4"
    )
    array[:] = values
    array.attrs["transform"] = [float(v) for v in product.transform]
    array.attrs["crs"] = "EPSG:32630"
    snapshot_id = session.commit("NDVI, site, June 2026")         # → snapshot id

    # --- publish ---
    # today (pipekit)
    # h = SHA-256(stable_json(state) ‖ 0x00 ‖ weights): the recipe's id
    recipe_hash = pipekit_ops.pipeline_hash(ndvi, b"")
    # one row in the product table: what, where, when, from what, by what
    record = {
        "id": "ndvi_site_2026-06",
        "start_time": "2026-06-01",
        "end_time": "2026-06-30",
        "bbox": list(site.bounds),
        "crs": "EPSG:32630",
        "href": "products.icechunk",
        "snapshot_id": snapshot_id,
        "recipe_hash": recipe_hash,
        "sources": [pathlib.Path(path).name for path in hits.gdf["filepath"]],
    }
    pq.write_table(pa.Table.from_pylist([record]), WORK / "products.parquet")

    # --- loop ---
    # the next pipeline's search is a query on the product table
    found = pq.read_table(WORK / "products.parquet").to_pylist()[0]
    reopened = repo.readonly_session(snapshot_id=found["snapshot_id"])
    again = zarr.open_array(reopened.store, path="ndvi")[:]       # → (H, W)

When to commit and publish
  • Write only for a scratch result you will look at once.
  • Commit when a result may be rewritten or appended to, or when a reader could arrive mid-write.
  • Publish when anyone else, or any later pipeline, should find the result by place and time.

Background: versions and identity for snapshots and commits; databases and catalogs for the product table.

The loop

What crosses each seam

BetweenWhat is handed overIn the running example
search → catalogfile names or URIs24 paths
catalog → savea GeoCatalog: rows of footprint, time, path6 rows
save → streamthe same catalog, pointing at nearby copies6 rows
stream → splita RasterField: a lazy array with a grid(2, 400, 500) uint16
split → apply → combinea list of Patch, each a small GeoArray with its place20 patches
combine → writeone GeoArray on the request's grid(400, 500) float64
write → commita store with uncommitted changes1 array, 4 chunks
commit → publisha snapshot idTF4JRH7NH25RB8FX2W9G
publish → the next searcha record: id, footprint, time, where, snapshot, recipe1 row

Because each seam is an object with a known shape, a stage can be replaced without touching its neighbours: a different archive behind search, a different operator in apply, a different store behind write.
