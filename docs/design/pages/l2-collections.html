Design note · catalog storage

Level 2 collections in GeoStack

12 Nov 2026 · J. Emmanuel Johnson

The CNG Forum 2026 talk by Tom Nicholas (Earthmover) and Sean Harkins (Development Seed) keeps a STAC-like catalog inside the same Zarr store as the scenes it indexes, so Icechunk can commit data and metadata together. This page checks what GeoStack already does against the code, then shows the smallest change that brings that idea in.

Summary

The carriers and lanes stay as they are. geocatalog already holds a table catalog, and geoarray and xrops already speak DataTree. The change is in where the catalog table lives and how products get written into it.

  • A.An Icechunk catalog backend. Today the table is a GeoParquet file sitting beside the files it points at. A third GeoCatalog backend keeps the table as columns in a meta/ group inside the repo, at a pinned snapshot.
  • B.A write half for the protocol. GeoCatalog is read-only, and registering a product is a second step after writing it. A transaction writes the product group and its row, then commits both or neither.
  • C.A scene-per-node raster loader. load_raster always mosaics onto the query grid. load_scenes returns one DataTree node per scene, each on its own grid, through the existing to_datatree.
  • D.One Zarr georeferencing convention. WriteZarr writes crs and transform attributes, while to_xarray writes a CF spatial_ref. Products in a shared repo should use one.
  • E.Virtual ingest of archives. Rows now name whole files. VirtualiZarr references would make a scene a group of virtual chunks, read like any Zarr array, with no copy.
  • F.A product catalog. Where products are recorded for others to find, in which database, and how pgstac fits: its own design doc, GeoStack product catalog.

End state. geocatalog owns the catalog on any of three backends and the write path; geoarray keeps its carriers and converters; geoops, xrops and pipekit do not change; the repo holds scenes, products and their index, versioned together, and is the truth that the product catalog is built from.

How a scene moves through the stack today

Two layers. The top one is the work you do: find, load, compute, write. The bottom one is what persists between tasks: the catalogs you search and the storage you read and write. Every arrow between the layers is a separate I/O call, and nothing ties one call to another.

Five verified gaps

  • 1

    The table and the data are separate artifacts. catalog.parquet and the scene files are written by different calls. A crash between them leaves a file with no row, or a row with no file, and nothing records which version of the table matched which files.

  • 2

    Rows point at whole files. CatalogRow.filepath names a COG or NetCDF file, so each read opens a file through rasterio or obstore. A row cannot point at a group of chunks.

  • 3

    No raster loader keeps scenes apart. load_raster always mosaics onto the query grid. Keeping each row on its own grid exists only for model states, through load_states(group_by=).

  • 4

    Two Zarr georeferencing conventions. WriteZarr stores crs as a string and transform as six numbers in group attributes; geoarray.to_xarray writes a CF spatial_ref with crs_wkt and GeoTransform. A reader of a shared repo would need both.

  • 5

    The protocol has no write half. GeoCatalog reads and combines catalogs; writing happens in build and storage functions outside it, so no backend can make a write atomic.

One doc lag found on the way: labeled_lane.md still lists LL-F3 as open, while to_datatree ships in geoarray 0.4.1.

Repository layout

One repository per collection. Every array in meta/ has shape (R,) for R rows and shares one chunking, so a chunk index acts like a Parquet row group.

s2-l2a-site.icechunk/
├── meta/                    # the catalog table, R rows
│   ├── id                   # str
│   ├── start_time           # datetime64[ms]
│   ├── end_time             # datetime64[ms]
│   ├── geometry             # bytes, WKB in EPSG:4326
│   ├── crs                  # str, the scene's native CRS
│   ├── key                  # str, the group path, e.g. scenes/S2A_20260601_T30SYJ
│   └── cloud_cover          # float32, any extra column
├── indexes/geometry         # optional R-tree over meta/geometry
├── scenes/<id>/              # bands (C, H, W) + CF spatial_ref; virtual or real chunks
├── products/<algo>/<id>/      # outputs, same convention, each with a meta/ row
└── cubes/<name>/             # aligned L3/L4 Datasets

The backend

The catalog is host-side and never traced, so it is a frozen dataclass rather than an Equinox module. A query keeps a row when its footprint meets the slice bounds B and its interval [t₀, t₁] meets the slice interval T.

# geocatalog/_src/backends/icechunk.py
"""A GeoCatalog whose table is the meta/ group of an Icechunk repository."""

import dataclasses
from collections.abc import Iterator
from typing import Any

import icechunk
import numpy as np
import pandas as pd
from jaxtyping import Bool

from geocatalog._src.base import CatalogRow
from geocatalog._src.geoslice import GeoSlice

# Shapes: R rows in meta/; K ≤ R rows kept by queries


@dataclasses.dataclass(frozen=True)
class IcechunkGeoCatalog:
    """Catalog rows read from meta/ at one snapshot.

    Args:
        repo: The repository holding meta/, the scenes and the products.
        uri: Where the repository lives, used to build each row's filepath.
        snapshot: The snapshot every read of this catalog names.
        keep: Rows kept by earlier queries; None keeps all R rows.
    """

    repo: icechunk.Repository
    uri: str
    snapshot: str
    keep: Bool[np.ndarray, "row"] | None = None

    def query(
        self,
        slice_: GeoSlice | None = None,
        *,
        bounds: tuple[float, float, float, float] | None = None,
        crs: Any | None = None,
        time: tuple[Any, Any] | pd.Interval | None = None,
    ) -> "IcechunkGeoCatalog":
        # proposed (A)
        meta_table = read_meta(self.repo, self.snapshot)            # → (R,) table
        # keep ⇔ footprint ∩ B ≠ ∅ ∧ [t₀, t₁] ∩ T ≠ ∅
        # proposed (A)
        overlaps = filter_rows(meta_table, slice_, bounds, crs, time)  # (R,) → (R,)
        # keep ← keep ∧ overlaps
        kept = overlaps if self.keep is None else self.keep & overlaps  # (R,) → (R,)
        return dataclasses.replace(self, keep=kept)

    def iter_rows(self, *, batch_size: int = 1024) -> Iterator[CatalogRow]:
        # proposed (A)
        records = kept_records(self, batch_size=batch_size)          # → (K,)
        for record in records:
            filepath = f"icechunk://{self.uri}@{self.snapshot}/{record.key}"
            # today (geocatalog)
            yield CatalogRow(
                filepath=filepath,
                geometry=record.geometry,
                interval=record.interval,
                crs=record.crs,
                extras=record.extras,
            )

The write half

Two protocols, kept small. DuckDB satisfies the first by wrapping append_files; only Icechunk satisfies the second.

# geocatalog/_src/base.py
"""The write half of the catalog protocol."""

from collections.abc import Mapping, Sequence
from typing import Any, Protocol

from geoarray import GeoArray


class GeoCatalogWriter(Protocol):
    """A catalog that can take new rows."""

    def append(self, rows: Sequence[CatalogRow]) -> None: ...


class CatalogTransaction(Protocol):
    """Writes carriers and their rows, visible only after commit.

    Raises:
        CatalogTransactionError: If the commit conflicts with another writer.
    """

    def put(
        self,
        key: str,
        carrier: GeoArray["band y x"],
        row: Mapping[str, Any],
    ) -> CatalogRow: ...

    def commit(self, message: str) -> str: ...


# proposed (B)
class CatalogTransactionError(GeoCatalogError, RuntimeError):
    """A commit lost a race with another writer on the same branch."""

The scene loader

# geocatalog/_src/formats/raster.py
import geoarray
import xarray as xr
from geoarray import GeoArray

from geocatalog._src.base import GeoCatalog
from geocatalog._src.geoslice import GeoSlice

# Shapes: K rows kept; per scene C bands on its own H × W grid


def load_scenes(
    catalog: GeoCatalog,
    slice_: GeoSlice,
    *,
    group_by: str = "id",
) -> xr.DataTree:
    """One DataTree node per row, each on the row's own grid.

    Algorithm:
        1. Open each kept row as a RasterSource: a file or an icechunk:// group.
        2. Read the slice's bounds on the row's native grid, with no reprojection.
        3. Put each carrier on its own node with geoarray.to_datatree.

    Args:
        catalog: The rows to load, usually the result of a query.
        slice_: The bounds to read from each scene.
        group_by: The row column whose value names each node.
    """
    scenes: dict[str, GeoArray] = {}
    # today (geocatalog)
    for row in catalog.iter_rows():                                 # (K,)
        # proposed (C)
        source = open_source(row.filepath)                          # → RasterSource
        # proposed (C)
        scene = read_bounds(source, slice_)                         # → (C, H, W)
        scenes[row.extras[group_by]] = scene
    # today (geoarray)
    tree = geoarray.to_datatree(scenes)                             # K → K nodes
    return tree

In action: matched filter over a month of scenes

The task: run the matched filter on every Sentinel-2 scene over a site in June 2026, keep the outputs, and make them findable. For each pixel, y ∈ ℝᶜ is its spectrum over C bands, μ ∈ ℝᶜ the background mean, Σ ∈ ℝᶜˣᶜ the background covariance, t ∈ ℝᶜ the methane target signature, and α̂ the enhancement. With fit_on_call=True, geoops fits μ and Σ on each scene. site_june is a GeoSlice over the site for June, and extract_row is the reader's own function that turns a file into a row.

from pathlib import Path

import geocatalog
import geocloud.cog
import geoops.matched_filter

# Shapes: R rows in the catalog; S scenes kept; C bands; H × W pixels per scene

# today (geocatalog)
catalog = geocatalog.open_catalog("s3://bkt/s2_site.parquet")   # → R rows
# today (geocatalog)
june = catalog.query(site_june)                                 # R → S rows
# today (geoops)
matched_filter = geoops.matched_filter.MatchedFilter(
    target=methane_target,
    fit_on_call=True,
)

product_paths: list[str] = []
# today (geocatalog)
for row in june.iter_rows():                                    # (S,)
    # today (geocloud)
    source = geocloud.cog.CogSource.open(row.filepath)
    # today (geocloud)
    scene = source.load()                                       # → (C, H, W)
    # α̂ = tᵀ Σ⁻¹ (y − μ) / (tᵀ Σ⁻¹ t)
    # today (geoops)
    enhancement = matched_filter(scene)                         # → (1, H, W)
    scene_id = Path(row.filepath).stem
    product_path = f"s3://bkt/products/mf/{scene_id}.tif"
    # today (geocloud)
    geocloud.cog.write_cog(enhancement, product_path)
    product_paths.append(product_path)

# second write: a crash before this line leaves COGs that no row points at
# today* (geocatalog)
geocatalog.build.append_files(
    "s3://bkt/mf_catalog/",
    product_paths,
    extract_row,
    crs="EPSG:4326",
    kind="raster",
    partition_by=[],
)

Testing gates

Each workstream merges only when its gate passes.

GateWorkstreamPasses when
A1 Query parityAOn the same rows, IcechunkGeoCatalog.query and DuckDBGeoCatalog.query return identical ids for 100 random GeoSlices, including slices in another CRS.
B1 AtomicityBA transaction that raises before commit leaves main at the same snapshot id, with no new group and no new row.
B2 ReproducibilityBAfter 10 later commits, opening the first snapshot returns the same rows and bit-identical arrays.
C1 Scene parityCEach load_scenes node equals the direct CogSource read of its file bit for bit, and from_datatree returns a Grid equal to the source's.
D1 One conventionDWriteZarr output opens through geoarray.from_xarray with the transform equal to 1e-9 and an equal CRS.
E1 Virtual parityEA virtual scene group reads bit-identical to its source COG or NetCDF on every band.

Sequencing and risks

Products first, because that is where the two-step write hurts today and where the scale is small. Source collections and virtual ingest follow once the backend has proven itself.

  D  one Zarr convention         B  write half (DuckDB append)
      │                              │
      ◆ D1                           ◆ B1
      └──────────────┬───────────────┘
                     │
  A  IcechunkGeoCatalog  ┃  C  load_scenes        (parallel)
                     │
                     ◆ A1 · B2 · C1
                     │
  E  virtual ingest of source scenes
                     │
                     ◆ E1
  • !

    Node count at mission scale. A year of HLS came to about 318 M nodes, and Icechunk's commit memory grows with the total node count (icechunk#2449). Fallback: one repo per collection and year, or keep GeoParquet as the index for source scenes and use Icechunk for products only.

  • !

    The query engine is a prototype. zarr-datafusion-search is early. Fallback: read meta/ into Arrow and filter with DuckDB, which geocatalog already depends on.

  • !

    Some formats do not virtualize well. Sentinel-2 JP2 tiles and EMIT's GLT geolocation are poor fits. Fallback: write those scenes as real Zarr chunks.

  • !

    Two indexes drift during migration. Fallback: the GeoParquet export of an Icechunk catalog is derived on demand and never edited by hand.

RecommendedDo D and B first, then A and C for products and derived collections. Keep source-scene catalogs on GeoParquet and DuckDB for now.
AlternativeMove source catalogs too, through E. It gives one index for everything but takes on the node-count risk on day one.
