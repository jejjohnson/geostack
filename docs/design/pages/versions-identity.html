GeoStack · background · bytes → id → history

Which data, which code and which settings made this map?

Pictures first. B12_v2_final_fixed.zarr is a name someone chose; it says nothing reliable about what is inside. This page builds the alternative step by step: ids that come from content, snapshots that never overwrite, history with branches and tags, commits that cannot half-happen, and products stamped with what made them. git, DVC, Icechunk and pipekit are all this one idea.

TL;DR

Never overwrite; name every state

  • A hash is a fingerprint of bytes. Same content, same id; one pixel changed, a different id.
  • A snapshot is a list of pointers to immutable pieces. A new version writes only the pieces that changed (4 of 121 chunks here) and a new list.
  • History is snapshots linked to their parents. A branch is a name that moves; a tag is a name that does not.
  • A commit is one pointer move, so it happens entirely or not at all, and two writers cannot silently overwrite each other.
  • Provenance is recording the ids of the data, code, environment and settings on every product.
  • The test: after reprocessing the site, tag v1 still reads 3449 where main reads 3450.

Identity: a name that comes from the content

import hashlib

# id = SHA-256(bytes)
band_id = hashlib.sha256(band.tobytes()).hexdigest()       # (5490, 5490) → 64 hex digits

A hash function maps any number of bytes to a fixed-length value. A good one (SHA-256, or the older SHA-1 and MD5 that git and DVC use) changes completely when one bit of input changes, and two different inputs sharing a hash is not something you will meet. An id made this way is a content address: anyone holding the bytes can recompute it and check.

When to identify by content, and when by name
  • Content id for anything that must be checked or cached: a file DVC tracks, a pipeline definition, model weights, a lock file.
  • Human name (a tag, a branch, a scene id) for anything people ask for. Names point at ids; they do not replace them.

Hashing costs a pass over the bytes, so very large arrays are identified per chunk or by the snapshot that holds them, not by one hash of everything.

Snapshots: versions that share what did not change

The rule that makes this work is immutability: a stored piece is never changed after it is written. Old versions cannot break, because nothing they point to is ever touched. The cost is that deleted data lingers until a clean-up (expiry and garbage collection) removes pieces no snapshot points to any more.

History: branches and tags

import icechunk
import zarr

# today (icechunk 2.3)
repo = icechunk.Repository.create(icechunk.local_filesystem_storage(path))

# today (icechunk 2.3)
session = repo.writable_session("main")
array = zarr.create_array(
    session.store, name="B12", shape=(5490, 5490), chunks=(512, 512), dtype="uint16"
)
array[:] = band                                            # 121 chunks, not yet visible
first = session.commit("ingest 2026-06-12")                # → snapshot id

# today (icechunk 2.3)
session = repo.writable_session("main")
array = zarr.open_array(session.store, path="B12")
array[2000:2100, 3050:3150] = reprocessed                  # touches 4 chunks
second = session.commit("reprocess site window")           # → snapshot id

# today (icechunk 2.3)
repo.create_tag("v1", snapshot_id=first)
old = zarr.open_array(repo.readonly_session(tag="v1").store, path="B12")
new = zarr.open_array(repo.readonly_session("main").store, path="B12")
When to use an id, a tag or a branch
  • Snapshot id in anything a machine records: a product's provenance, a training run, a cache key.
  • Tag for a state people cite: a release, the data behind a paper.
  • Branch for a line of work that moves: main for the collection, a side branch to trial a reprocessing before it replaces main.

Reading “latest” from a branch is convenient and not reproducible: record the id it resolved to.

Commits: all or nothing, one writer at a time

This is the same promise a database transaction makes (databases and catalogs), built from the only safe multi-object pattern a bucket offers (object storage). It is what lets a catalog row and the chunks it describes appear together, or not at all.

Provenance: ids on the product

import pipekit_ops.hashing

# today (pipekit)
# h = SHA-256(stable_json(state) ‖ 0x00 ‖ weights)
recipe_id = pipekit_ops.hashing.pipeline_hash(pipeline, weights)   # → 64 hex digits

pipekit already computes the code half. What is missing today is writing it, with the data snapshot id, onto each output; that is the recipe stamp in the recipe registries design.

One row differs. Icechunk's ids are generated, not derived from content: writing the same band into a second repository gave a different snapshot id (measured). Its ids tell you which commit, not which bytes. If you need to prove two arrays are equal, hash them; if you need to say which state you read, the snapshot id is enough.
