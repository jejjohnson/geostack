GeoStack · background · key → bytes

What is a bucket, and why can't you append to a file in it?

Pictures first. S3, Azure Blob Storage and Google Cloud Storage are not disks. Each is a dictionary from a name to a blob of bytes, reached over HTTP with five operations. Cloud-native formats, catalogs and versioned stores are all designed around what those five can and cannot do.

TL;DR

A dictionary over HTTP

  • A bucket maps keys to objects. There are no folders; a “/” in a key is just a character.
  • Five verbs: PUT a whole object, GET it (or a byte range), HEAD its metadata, LIST keys by prefix, DELETE. No append, no edit in place, no rename.
  • Range requests are what make COG, Parquet and Zarr sharding work: fetch the index, then only the bytes you need.
  • Listing is slow (1 000 keys per page, one page after another), so serious layouts keep their own index.
  • One PUT is atomic; several are not. Anything that must change together needs a design: write new objects, then swap one pointer with a conditional PUT.
  • Every request costs time and money, so fewer, larger, concurrent requests from the same region win.

Keys, not folders

An object is a blob of bytes plus a little metadata (size, time, a fingerprint called the ETag). A key is its full name. A bucket (Azure: container) holds the keys. The store keeps keys sorted, which is why a prefix search is possible and nothing else is: you cannot ask for “every B12.tif” without walking every scene prefix.

Five verbs

The missing operations matter more than the present ones. No append means a growing array cannot be one growing file, so Zarr stores one object per chunk. No rename means the usual “write to a temp file, then rename” trick for safe writes does not exist. No lock means two writers cannot take turns unless the format gives them a way.

Range requests: reading part of an object

A range request is a GET with a header naming the bytes wanted. It costs about the same as any other request, whatever the object's size. A format is cloud-native when its index sits where one small range request can fetch it and points to byte ranges for everything else. The storage formats page shows how COG, GeoParquet and Zarr each do that.

import obstore

# not pinned (obstore)
store = obstore.store.S3Store("sentinel-cogs", region="us-west-2", skip_signature=True)
key = "sentinel-s2-l2a-cogs/31/T/CJ/2026/6/S2A_31TCJ_20260612_0_L2A/B12.tif"

# not pinned (obstore)
head = obstore.head(store, key)                       # size, last_modified, e_tag
# not pinned (obstore)
header = obstore.get_range(store, key, start=0, end=16_384)       # → 16 384 B
# not pinned (obstore)
tiles = obstore.get_ranges(store, key, starts=starts, ends=ends)  # → 4 buffers

# not pinned (obstore)
# fails if the key already exists: a conditional PUT
obstore.put(store, "models/_tags/v3", b"<hash>", mode="create")

Each request has a fixed cost of tens of milliseconds before the first byte arrives, so a read is priced in requests more than in bytes. Two consequences: merge nearby ranges into one request, and send independent requests at the same time (the parallelism page measures that: 121 tile fetches drop from 6.4 s to 0.23 s).

Listing is the slow verb

When to list, and when not to
  • List to discover what exists once: building a catalog, an inventory, a clean-up job.
  • Do not list on the read path. Read an index instead: a STAC item, a geocatalog table, Zarr consolidated metadata, an Icechunk manifest.
  • Design keys for the prefix you will list by: tile/year/month/scene/ lets you list one month of one tile cheaply.

Stores also limit request rates per prefix (S3 documents 3 500 writes and 5 500 reads per second) and answer “slow down” beyond that, so a retry with backoff belongs in any client.

Writing safely: one PUT, or a pointer swap

S3, Azure and GCS are strongly consistent: once a PUT returns, every later GET and LIST sees it. That covers one object. For several objects that must change together, the pattern is always the same: write the new objects under keys nobody reads yet, then make them visible with one conditional write. Icechunk commits this way; the versions and identity page builds on it.

When a plain bucket is enough, and when it is not
  • Enough: write-once products, one object per output, readers that find objects through a catalog.
  • Not enough on its own: several objects that form one logical thing (a Zarr store, a model with weights and metadata), or more than one writer. Use a transactional layer (Icechunk, a database) on top.

A crash between PUTs is not rare at scale: at 60 500 objects per ingest, plan for it.
