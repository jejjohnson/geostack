GeoStack · background · one worker → many

Why do 121 tiles take 6.4 s, and what gets them to 0.23 s?

Pictures first, maths folded away. Threads, processes and async are three ways to do more than one thing at a time in Python. Which one helps depends on a single question: is your program waiting, or is it computing? This page answers it for one read, with measured numbers.

TL;DR

Waiting and computing need different tools

  • Two kinds of work. Waiting on a network or disk (I/O-bound) leaves the CPU free. Computing (CPU-bound) keeps it busy. A cloud read is mostly waiting.
  • Async overlaps waits on one thread. It never computes two things at once.
  • Threads overlap waits too, and also overlap computing when the code runs inside NumPy, zlib or Rust, which release Python's interpreter lock (the GIL).
  • Processes overlap any computing, including pure Python, and pay for it in start-up time and copying data between them.
  • Two more levels. Vectorising (NumPy, JAX) speeds up one worker, often by more than any of the above. Distributing (dask, batch jobs) adds machines.
  • The test: reading 121 tiles drops from 6.40 s to 0.23 s with 64 threads, and stays at 6.39 s if one blocking call hides inside async code.

The problem: one thing at a time

waiting on the network (fetch, 50 ms)computing (decode, 2.3 ms)
# Shapes: N = 121 tiles; P = 512 px tile side

# user
def fetch(index: int) -> bytes: ...          # one range request, ~50 ms of waiting
# user
def decode(blob: bytes) -> np.ndarray: ...   # inflate + undo predictor  → (P, P)

# T = N (t_fetch + t_decode)
tiles = [decode(fetch(index)) for index in range(121)]      # → 121 × (P, P)

Two kinds of work

A program is I/O-bound when its time goes on waiting for something outside it: a network reply, a disk. It is CPU-bound when its time goes on computing. Our read is 96 % waiting, so the first thing to do is stop waiting for one tile before asking for the next.

How much can overlapping the waits buy? (Amdahl's law)

Let \(p\) be the fraction of the serial time that can be overlapped, and \(k\) how many of those pieces run at once. The speed-up is

\[ S(k) = \frac{1}{(1 - p) + p / k} \]

Here the waits are the part we overlap, so \(p = t_f / (t_f + t_d) = 50 / 52.34 = 0.955\). With every wait overlapped, \(k \to \infty\) and

\[ S_{\max} = \frac{1}{1 - p} = 22.4 \]

The floor is the computing that is left, \(N t_d = 121 \times 2.34\ \mathrm{ms} = 0.28\ \mathrm{s}\). To go below it, the decodes themselves have to run in parallel.

Concurrency is not parallelism

Concurrency is dealing with several things in the same period. Parallelism is doing several things at the same instant. A single core can be concurrent; only several cores can be parallel.

Part 1 · The three mechanisms

Async: one thread that never waits idle

waiting on the network (fetch, 50 ms)computing (decode, 2.3 ms)

An event loop runs on one thread. Each await is a point where a task says "I am waiting; run someone else". The loop keeps a list of what is waiting on what, and resumes each task when its reply arrives. No locks are needed, since only one task runs at a time.

import asyncio

async def read_tile(index: int, limit: asyncio.Semaphore) -> np.ndarray:
    async with limit:                        # at most 16 requests in flight
        blob = await afetch(index)           # the loop runs other tiles meanwhile
    return decode(blob)                      # blocks the loop for ~2.3 ms

async def read_all() -> list[np.ndarray]:
    limit = asyncio.Semaphore(16)
    return await asyncio.gather(*(read_tile(i, limit) for i in range(121)))

tiles = asyncio.run(read_all())                             # → 121 × (P, P)

Measured: 0.60 s with 16 in flight, 0.38 s with 64. The remaining time is mostly the 0.28 s of decoding, queued on the one thread. Moving the decode to a thread removes that queue (0.44 s with 16 in flight):

    # hand the computing to a thread so the loop keeps serving requests
    return await asyncio.to_thread(decode, blob)
Watch out

One blocking call inside a coroutine stops every task. Replacing await asyncio.sleep with time.sleep in the example (the same as calling requests.get or a slow NumPy routine in a coroutine) gives 6.39 s: serial speed, with async syntax.

When to use async

Use async when the work is many waits and the library you call is already async.

  • Thousands of small requests: tile and chunk fetches, STAC searches. A waiting task costs kilobytes; a waiting thread costs a stack.
  • Servers: a tile server or API handling many clients at once.
  • Async-native readers: obstore, async-geotiff and Zarr v3 stores expose async methods.

Less suited to computing (it gives none in parallel), and to code that mixes with blocking libraries: every function on the path has to be async.

Threads: several workers, one shared memory

waiting on the network (fetch, 50 ms)computing (decode, 2.3 ms)

A thread is a worker inside your process. Threads share all memory, so passing an array between them costs nothing, and the operating system switches between them whenever one waits. Ordinary blocking code works unchanged.

import concurrent.futures

def read_tile(index: int) -> np.ndarray:
    return decode(fetch(index))              # ordinary blocking code

with concurrent.futures.ThreadPoolExecutor(max_workers=16) as pool:
    tiles = list(pool.map(read_tile, range(121)))           # → 121 × (P, P)

Measured: 1.64 s with 4 threads, 0.45 s with 16 (14×), 0.23 s with 64 (27×).

The GIL: why threads sometimes do not compute in parallel

CPython has a global interpreter lock (GIL): only one thread at a time may run Python bytecode. A thread gives it up when it waits on I/O, which is why threads work for fetching. Native libraries also give it up while they compute, which is why NumPy, zlib, zarr codecs and Rust extensions do run in parallel on threads. Pure-Python loops do not.

Decode-only, 121 tiles (measured)Serial2 threads2 processes
Pure-Python loop (holds the GIL)0.29 s0.48 s0.25 s
zlib + NumPy (release the GIL)0.28 s0.14 s0.19 s

Python 3.13 added an optional free-threaded build without the GIL, and 3.14 made it officially supported. On it, pure-Python threads do run in parallel, provided every compiled dependency supports it. The numbers on this page are from the standard build.

When to use threads

Use threads when the work is waiting, or computing inside native code, and the code is ordinary blocking Python.

  • Fetching files or tiles with a blocking client (rasterio, requests, fsspec).
  • Array work in NumPy, SciPy or numcodecs: dask's default scheduler for arrays is a thread pool for this reason.
  • Anything where the data is large: threads share it without copying.

Less suited to pure-Python computing (the GIL), and to code that changes shared state: two threads writing the same object need a lock. Also watch for oversubscription: 8 dask threads each calling a BLAS routine that starts 8 threads of its own is 64 threads on 8 cores.

Processes: separate interpreters

A process is a separate running Python with its own memory and its own GIL. Several processes compute in parallel whatever the code is. The price is that they share nothing: every task and result is serialised (pickled), sent, and rebuilt.

import concurrent.futures

# read_tile must be importable (top level of a module), and its
# arguments and results must pickle
if __name__ == "__main__":
    with concurrent.futures.ProcessPoolExecutor(max_workers=2) as pool:
        tiles = list(pool.map(read_tile, range(121), chunksize=8))

Measured on the full read: 3.25 s with 2 processes, 0.54 s with 16. For a job that is 96 % waiting, processes are just expensive threads. They pay off in the pure-Python row of the table above, where threads made things slower.

When to use processes

Use processes when the slow part is computing in Python itself, or in a library that is not thread-safe.

  • Pure-Python per-item work: parsing, custom loops, per-file logic.
  • Libraries with global state that cannot be shared between threads: some HDF5 and GDAL builds.
  • Isolation: a crash or memory leak in one worker does not take down the rest.

Less suited to large arrays passed back and forth (each crossing is a copy), to short tasks (start-up is tens of milliseconds, and far more once the worker imports NumPy or JAX), and to notebooks, where functions defined in a cell may not pickle. Prefer the spawn start method with threads or JAX in the parent.

Part 2 · Below and above

Below: make one worker faster

# ρ = (DN − 1000) / 10 000

# Today: one Python step per pixel
reflectance = [[(dn - 1000) / 10000 for dn in row] for row in tile.tolist()]
# After: one array expression
reflectance = (tile.astype(np.float32) - 1000) / 10000      # (P, P) → (P, P)

Vectorising replaces a Python loop with one call that loops in compiled code, often using the CPU's SIMD instructions (several numbers per instruction). jax.vmap and jax.jit do the same for whole functions, and a GPU does it across thousands of cores. None of this is a thread, a process or an event loop in your code, and it usually comes first.

Above: more machines

A distributed system is processes on several machines with a scheduler that hands out tasks and tracks results. dask does this with a task graph; a batch service does it with one job per scene. The costs of processes return, larger: data crosses a network, so workers should read from object storage themselves and send back small results.

When to go below or above
  • Vectorise whenever a loop body is arithmetic on array elements.
  • Distribute when one machine's cores, memory or network link is the limit, and the work splits into independent pieces (per scene, per tile, per chunk).

Distribution adds failure modes a single machine does not have (lost workers, partial results), so each task should be safe to run twice.

Whichever you pick, bound it. 60 500 unbounded requests will be throttled by the object store, and 60 500 queued results can exhaust memory. A limit on work in flight (a semaphore, a worker count, a submission window) is part of the design.

The 64-thread row shows the switch from I/O-bound to CPU-bound: once the waits overlap enough, the decodes on two cores set the pace, and pool overhead accounts for the rest of the gap to the measurement. The async model is an upper bound, since waits continue while the loop decodes.

Calling async code from blocking code

The place the mechanisms meet is also where notebooks break. asyncio.run starts a loop, and a thread can run only one:

# In a script: fine
tiles = asyncio.run(read_all())

# In a notebook cell, a FastAPI handler or a pytest-asyncio test:
#   RuntimeError: asyncio.run() cannot be called from a running event loop
# In a notebook, await directly instead:
tiles = await read_all()

Libraries that offer a blocking API over async internals solve this once, with a loop on a background thread. zarr does it with its zarr_io thread, and geocloud with _run_coroutine_safely. That pattern is why xr.open_zarr works in a notebook without an await in sight.
