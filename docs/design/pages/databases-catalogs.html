Which of 100 000 scenes cover my site in June?

Pictures first. A catalog answers “which files do I need?” before any pixel is read. This page covers what sits under one: tables, indexes, row and column storage, transactions, where a database lives, and what STAC and pgstac add. One question runs through all of it, with measured times.

TL;DR

A table, an index, and a promise about writes

  • A catalog is a table: one row per scene, typed columns, a unique id, and a column pointing at the data.
  • An index is a sorted or grouped copy of a column that lets a query skip most rows: a B-tree for time and ids, a spatial tree for footprints.
  • Row stores (PostgreSQL, SQLite) are built for finding and changing single rows. Column stores (Parquet, DuckDB) are built for reading a few columns of many rows.
  • A transaction makes several changes succeed or fail together. An upsert makes a write safe to repeat.
  • A database can be a server, a library inside your program, or just a file. The SQL is nearly the same; who may write is not.
  • STAC is a shared vocabulary for catalog rows; pgstac stores STAC in PostgreSQL. The test: the June query drops from 9.1 ms to 0.28 ms with one index.

A table

A schema is the list of columns and their types. A primary key is a column whose value is unique per row; it is how a product record, a STAC item and a file on disk all refer to the same scene. Nothing else on this page works without one.

-- the catalog
CREATE TABLE scenes (
    id        TEXT PRIMARY KEY,
    datetime  TIMESTAMP NOT NULL,
    geometry  GEOMETRY(Polygon, 4326) NOT NULL,   -- PostGIS type
    cloud     REAL,
    href      TEXT NOT NULL
);
CREATE INDEX scenes_time ON scenes (datetime);              -- B-tree
CREATE INDEX scenes_geom ON scenes USING GIST (geometry);   -- spatial

-- scenes over the site in June 2026
SELECT id, href FROM scenes
WHERE datetime >= '2026-06-01' AND datetime < '2026-07-01'
  AND ST_Intersects(geometry, ST_SetSRID(ST_Point(-0.40, 39.45), 4326));

Indexes: how a query skips rows

The time index wins here because June is the more selective filter (2 120 rows against 1 178). The database's query planner makes that choice for you when both indexes exist. At 100 000 rows every method answers in milliseconds; the gap grows with the table, since a scan grows with the row count and an index lookup with its logarithm.

When to add an index
  • Columns you filter or join on: time, geometry, ids, a collection name.
  • Tables that are read far more than written: a catalog is exactly that.

Skip indexes on columns you only ever display, and on small tables: below a few thousand rows a scan is as fast.

Row stores and column stores

The two layouts suit two kinds of question. “Give me scene S2_081302” or “mark this scene processed” touches one row: a row store finds it through the primary key and changes it in place. “Mean cloud cover per month” touches one column of every row: a column store reads that column alone, and skips whole row groups whose min and max rule them out (the June query read 1 of 10).

import duckdb

# the same question, asked of a file; no server, no load step
hits = duckdb.sql("""
    SELECT id, href FROM 'catalog.parquet'
    WHERE datetime >= TIMESTAMP '2026-06-01' AND datetime < TIMESTAMP '2026-07-01'
      AND x0 <= -0.40 AND x1 >= -0.40 AND y0 <= 39.45 AND y1 >= 39.45
""").fetchall()                                             # → 23 rows
When to use which
  • Row store (PostgreSQL, SQLite): records that change, many small reads and writes, several writers, a service behind an API.
  • Column store (Parquet + DuckDB): write once, read many; scans and statistics; a catalog you ship as a file next to the data.

Parquet has no update: changing one row means rewriting a file. That is the price of the 5× smaller size and the faster scans.

Transactions and upserts

Databases promise four things about a transaction, known as ACID: it is atomic (all or nothing), leaves the data consistent with its rules (types, unique keys), is isolated from other transactions running at the same time, and is durable once committed. Atomic and isolated are the two the storage designs lean on.

-- insert, or update if the id is already there: safe to run twice
INSERT INTO scenes (id, datetime, geometry, cloud, href)
VALUES (:id, :datetime, :geometry, :cloud, :href)
ON CONFLICT (id) DO UPDATE
SET href = EXCLUDED.href, cloud = EXCLUDED.cloud;

An upsert inserts a row or updates the one with the same key. Running it twice gives the same table as running it once, which is what a retried or restarted pipeline needs.

SQL, drivers and ORMs

You reach a database through a driver that sends SQL. A toolkit such as SQLAlchemy lets you describe tables in Python and builds the SQL for you; its ORM layer goes further and maps rows to objects. Two rules keep that safe.

import sqlalchemy as sa

metadata = sa.MetaData()
# map only the columns this program uses; the table may have more
scenes = sa.Table(
    "scenes", metadata,
    sa.Column("id", sa.Text, primary_key=True),
    sa.Column("datetime", sa.DateTime, nullable=False),
    sa.Column("href", sa.Text, nullable=False),
)
query = sa.select(scenes.c.id, scenes.c.href).where(
    scenes.c.datetime.between("2026-06-01", "2026-06-30")
)
  • A Python model may describe a subset of a table's columns. Reads work as they are. Inserts work as long as every column the model leaves out is nullable or has a default.
  • One tool owns the table definitions. Either your migrations create and alter the tables, or another system does (pgstac owns its own schema). Two owners drift apart.

STAC and pgstac

A STAC item is one row of the catalog written as GeoJSON, with agreed names. The mapping to this page's table is direct: id is the primary key, geometry and bbox the footprint, properties.datetime the time, and each asset an href to a file such as the B12 COG.

When to use STAC, and pgstac
  • STAC when anyone outside your code will search the catalog: other teams, QGIS, pystac-client, a web map.
  • pgstac when you need a live STAC API over millions of items. Write to it through its functions (pgstac.upsert_items), not with an ORM over its tables: it stores items in a compacted form across partitions, and the functions are its interface.
  • stac-geoparquet when the catalog is published in bulk and read for analysis.

A working catalog inside one pipeline does not need STAC; it needs the table. Add STAC at the boundary where others read.
