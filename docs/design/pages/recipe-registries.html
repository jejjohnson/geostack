Design note · recipes and registries

pipekit recipe registries

12 Nov 2026 · J. Emmanuel Johnson

pipekit already treats a pipeline as data: it serialises to JSON, hashes to an id, and lives in a registry with tags. This page checks how far that goes today, then puts pipekit's four storage seams (model registry, cache store, training data, product stamp) on Icechunk, so code and data are versioned the same way.

Read from main on 12 Nov 2026. One of three pages: Level 2 collections in GeoStack (the repo, its index and transactions, A–E), GeoStack product catalog (F, K, L) and this one (G–J). Letters never repeat across them.

Summary

None of pipekit's operators change, and pipeline_hash keeps its meaning. What changes is where pipekit persists things, and what a product records about the code that made it.

  • G.Products that name their recipe. pipekit stores operators by pipeline_hash, but no product records which recipe made it, and the hash covers configuration, not code. A small stamp (hash, registry, package versions, lockfile hash) goes into every product row.
  • H.A model registry on Icechunk. registry.store writes up to four objects one after another, so a crash can leave half an entry. An IcechunkModelRegistry makes each store one commit.
  • I.A cache store on Icechunk. Cache already writes to any named Store, and pipekit leaves carrier-specific stores to its sister packages. An IcechunkStore keeps array results as Zarr instead of pickles, and shares them across machines.
  • J.Training data pinned to a snapshot. TrainingDataset.content_hash hashes the dataset's configuration, so it cannot tell two versions of the same files apart. A dataset read from a repo folds the snapshot id into its hash.

End state. pipekit-ops stays dependency-free; pipekit-experiment gains an Icechunk registry and the recipe stamp behind an [icechunk] extra; geocloud gains a carrier-aware Icechunk store; pipekit-train datasets can name a snapshot. A model, a cache entry, a training set and a product are each one commit with an immutable id.

Where pipekit persists things today

Three layers. At the top, what makes a pipeline a recipe. In the middle, the three places pipelines run. At the bottom, the four places their results and records land. Every store at the bottom is a separate system with its own write semantics.

Five verified gaps

  • 1

    A registry store is several writes. store writes operator.json, then weights.bin, then metadata.json, then the tag file. LocalModelRegistry makes each file atomic, not the set, and S3ModelRegistry says it is only as atomic as its backing store.

  • 2

    No array-aware cache store. DirectoryStore pickles one file per key, and store.py leaves Zarr, COG and object-store stores to the sister packages; none exists in geotoolz yet.

  • 3

    A dataset hash names its config, not its data. The default content_hash cannot tell two versions of the same files apart, so TrainingArtifact.dataset_hash does not pin the data unless a subclass folds a version in. DVC can, but per file and through git.

  • 4

    Products do not name their recipe. Nothing writes a pipeline_hash next to a product, so "which code made this map" has no lookup.

  • 5

    The hash covers config, not code. op.state has no package version, so the same MatchedFilter config hashes alike under two geoops releases. Versions are kept only in an artifact's backend_info and deps_lock.

G · recipes

Recipes are versioned like data

The repo and the recipe registry are the same pattern on two kinds of thing.

A product is a recipe applied to inputs

Write α = R(x) for a product α made by recipe R from inputs x. Provenance is complete when the record names all three, each by an immutable id:

  inputs x     derived_from links → source items         product catalog, F
               scenes at repo@snapshot                     L2 page, A
      │
  recipe R     pipeline_hash → registry.load(hash)          today
               package versions + lockfile hash             G
      │
  product α    products/mf/<id> at repo@snapshot          L2 page, B
               one product-catalog record naming x and R    F + G

With all three, a product can be rebuilt and checked: load R by hash, open x at its snapshot, run, and compare with α. That is gate G1.

The one subtlety: config is not code

pipeline_hash covers op.state, the configuration. Two geoops releases with different MatchedFilter code but the same config share a hash. Changing the hash to include versions would move every id already in a registry, so keep the hash and record the versions beside it.

RecommendedKeep pipeline_hash as the recipe id. Stamp each product with the hash, the versions of the packages it imported and a hash of the lockfile; keep the full InferenceArtifact in the registry next to the recipe.
AlternativeFold versions into the id, a recipe-and-environment hash. One id says everything, but every patch release mints a new id for an unchanged recipe, and old registry entries stop matching.
# pipekit_experiment/_src/stamp.py
"""What a product records about the recipe that made it."""

import dataclasses
from importlib import metadata

import pipekit_ops
import pipekit_ops.hashing

# Shapes: P packages pinned


@dataclasses.dataclass(frozen=True)
class RecipeStamp:
    """The recipe behind a product: its id, where it lives, what ran it.

    Args:
        pipeline_hash: The recipe id, pipekit_ops.pipeline_hash(op).
        registry_uri: The registry that holds the recipe.
        versions: Package name to installed version, for the packages it uses.
        lock_hash: sha256 of the lockfile the run used.
    """

    pipeline_hash: str
    registry_uri: str
    versions: dict[str, str]
    lock_hash: str


# proposed (G)
def stamp(
    op: pipekit_ops.Operator,
    *,
    registry_uri: str,
    packages: tuple[str, ...],
    lockfile: str,
) -> RecipeStamp:
    """Build the stamp a transaction writes into every product row."""
    # h = sha256(stable_json(op.state) ‖ 0x00)
    # today (pipekit-ops)
    recipe_hash = pipekit_ops.pipeline_hash(op)                     # → 64 hex
    # not pinned (importlib)
    versions = {name: metadata.version(name) for name in packages}  # → P
    # h_lock = sha256(lockfile)
    # today (pipekit-ops)
    lock_hash = pipekit_ops.hashing.sha256_hex(lockfile)            # → 64 hex
    return RecipeStamp(recipe_hash, registry_uri, versions, lock_hash)

In the product catalog the stamp becomes a few properties beside the lineage links: pipekit:pipeline_hash, pipekit:registry, pipekit:lock_hash, and processing:software for the versions. In a PostGIS table, pipeline_hash earns its own indexed column, so "everything this recipe made" is one query.

H · model registry

A model registry where a store is one commit

_ModelRegistryBase keeps all the user-facing logic (hashing, verify-on-load, tag merging) and asks a backend for six primitives: _exists, _read_text, _write_text, _read_bytes, _write_bytes, _children, plus _where for messages. An Icechunk backend implements those against one writable session and wraps store and tag in a commit, so a crash leaves no half entry and every model version is a snapshot.

  models.icechunk/
  ├── <hash>/operator.json     the state, as the other backends write it
  ├── <hash>/weights.bin       optional blob (JaxModelOp.serialize_weights)
  ├── <hash>/metadata.json     tags merged across stores
  └── _tags/<name>             the hash a name points at
# pipekit_experiment/_src/icechunk_registry.py
"""A model registry whose every store and tag is one Icechunk commit."""

import contextlib
from collections.abc import Iterator

import icechunk

from pipekit_experiment.registry import _ModelRegistryBase

# Shapes: B bytes of weights


class IcechunkModelRegistry(_ModelRegistryBase):
    """Operators and weights in an Icechunk repo, one commit per store.

    Args:
        repo: The repository that holds the models.
        branch: The branch stores commit to.
    """

    def __init__(self, repo: icechunk.Repository, *, branch: str = "main") -> None:
        self.repo = repo
        self.branch = branch
        self._session = None

    @contextlib.contextmanager
    def _transaction(self, message: str) -> Iterator[None]:
        # not pinned (icechunk)
        self._session = self.repo.writable_session(self.branch)
        try:
            yield
            # not pinned (icechunk)
            self._session.commit(message)
        finally:
            self._session = None

    def store(self, model_op, *, name=None, tags=None, weights=None) -> str:
        # proposed (H)
        with self._transaction(f"store {name or 'model'}"):
            # today (pipekit-experiment)
            return super().store(model_op, name=name, tags=tags, weights=weights)

    def _write_bytes(self, data: bytes, *parts: str) -> None:
        # proposed (H): one uint8 array per object, in the open session
        write_object(self._session.store, "/".join(parts), data)    # → (B,)

Only two of the primitives are shown; the rest follow the same shape. tag gets the same transaction wrapper. Weights stay one blob here so the hash is unchanged; storing each array leaf as its own Zarr array would make them inspectable, but would need its own hash rule.

I · cache store

A cache that is shared, typed and versioned

Cache(op, store="scenes") names a store, and store_scope binds the name to a real store around the call, so where results go is a deployment choice outside the pipeline's config and its hash. An Icechunk store fits that seam without touching pipekit-ops, which stays free of third-party dependencies.

# geocloud/_src/icechunk_store.py

import pipekit_ops

# Shapes: S scenes; C bands; H × W pixels

Two things to keep in mind. A commit per save would be slow, so the store batches commits and closes with one. And a byte entry is still a pickle: load cache entries only from repos you trust, as with DirectoryStore today.

J · training data

Training data pinned to a snapshot

TrainingDataset.content_hash is what CachedDataset keys on and what TrainingArtifact.dataset_hash records. Its docstring already asks datasets with external state to fold that state in; a dataset read from a repo folds in the snapshot id, so the hash changes when the data does.

# pipekit_train/_src/snapshot_dataset.py
"""A TrainingDataset read from an Icechunk repo at one snapshot."""

import pipekit_train
import pipekit_train.dataset


class SnapshotDataset(pipekit_train.TrainingDataset):
    """Samples read from repo@snapshot; the snapshot is part of its identity.

    Args:
        uri: Where the repository lives.
        snapshot: The snapshot every sample is read from.
    """

    def content_hash(self) -> str:
        # h = sha256(type ‖ config ‖ snapshot)
        config = {**self.get_config(), "snapshot": self.snapshot}
        # today (pipekit-train)
        return pipekit_train.dataset.hash_config(type(self).__qualname__, config)
RecommendedIcechunk snapshots for array training data, read through SnapshotDataset; DVC stays for the files that are not arrays (label exports, configs, notebooks).
AlternativeDVC for everything. One tool, but it versions whole files through git, so a new month of scenes re-hashes files instead of adding chunks.

Testing gates

Each workstream merges only when its gate passes.

GateWorkstreamPasses when
G1 ReproduceGLoading the recipe by pipeline_hash and the inputs at their snapshot, under the stamped lockfile, and running again gives arrays bit-identical to the product.
G2 Stable idGpipeline_hash(loads(dumps(op))) == pipeline_hash(op) for every operator in the recipe, and every product row carries a hash that registry.load resolves.
H1 ParityHThe registry test suite passes unchanged on all three backends, and the same operator stores under the same hash on each.
H2 Atomic storeHA store that raises after operator.json leaves the branch at its old snapshot, and load of the hash raises KeyError.
I1 Cache parityIOver one run, hits, misses and outputs are identical with DirectoryStore and IcechunkStore; a GeoArray read back has an equal Grid.
I2 RestartIA new process bound to the same repo and branch hits every entry the first process saved.
J1 Pinned dataJcontent_hash changes when the snapshot or the config changes, and only then.

Sequencing and risks

The stamp first, since it needs no new dependency and closes the provenance loop the product catalog opens. Then the registry, the smallest change with the clearest win.

  G  recipe stamp
      │
      ◆ G1 · G2
      │
  H  Icechunk model registry
      │
      ◆ H1 · H2
      │
  J  snapshot datasets  ┃  I  Icechunk cache store     (parallel)
      │
      ◆ J1 · I1 · I2
  • !

    Overriding store leans on a private base. _ModelRegistryBase is underscored. Fallback: give it a public hook, a _transaction context that defaults to doing nothing, so each backend opts in.

  • !

    Commit cost. A commit per cache save or per small model is slow on object storage. Fallback: batch commits in the store, and keep DirectoryStore for hot local caches.

  • !

    Two kinds of tag. Registry tags (_tags/<name>) move freely; Icechunk tags are meant to be stable. Fallback: registry tags stay data inside the repo, and Icechunk tags mark releases only.

  • !

    Pickles in a shared repo. A shared cache spreads pickles further than a local directory. Fallback: carriers always go as Zarr, and byte entries load only from repos on an allowlist.
