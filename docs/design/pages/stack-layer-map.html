GeoStack layer map

The same number of layers as today, cut by a different test. Core holds the maths and plumbing that knows no geography, so GeoML dissolves into it. GeoNumerics holds geophysical maths on plain arrays; the data toolkits sit above it and wrap its kernels in carriers; the physics models sit on top.

Beneath Core sit the third-party foundations the whole stack is built on: JAX, Equinox, lineax, optimistix, diffrax, optax, NumPyro and the array libraries. The function-approximation core, functax, goes in Core tier 0, the one placement where geotoolz and finitevolX can both import it; integrix (integration over time, space and spectrum) and argminax (optimisation with uncertainty at the optimum) sit just above it.

GeoStack

GeoStack here means exactly geotoolz + xrtoolz, the two workspaces below; the whole project keeps the name too, and pipekit, which today's geostack dependency graph puts in its GeoStack layer, moves to Core. Real data: carriers, CRS, I/O and products. Two uv workspaces, eight packages, about 150k lines: the geotoolz workspace (six packages, raster and swath data on GeoArray) and the xrtoolz workspace (two packages, data cubes on xarray, with a third proposed below). Each package installs on its own; the geotoolz and xrtoolz umbrellas hold no code. georeader is not one of them: it is spaceml-org's GDAL reader, reached only through geoarray.interop.georeader as an engine behind a few readers and warps, so it sits with the third-party foundations.

The gap: a floor for the xarray side. On the GeoArray side the carrier's vocabulary lives at the bottom, in geoarray, and geotoolz has a rule that geoops never depends on geoproducts. On the xarray side the same vocabulary is split between a reader and the operators: the CF Variable registry and the typed vocabulary live in xrproducts.types, CF validation in xrops.cf, CRS and subsetting in xrops.geom. So xrops imports a reader package (eight imports of xrproducts.types) to name a variable, which is exactly the edge geotoolz forbids. The proposal is one small package at the bottom of the xarray side, here called xrcf (xrtoolz-cf; the name is open): CF conventions and the Variable registry, coordinate and CRS conventions, validation, subsetting and the typed vocabulary. It is not a new carrier (xarray is the carrier) but the conventions that make a DataArray a carrier. xrproducts and xrops both import it, and xrops stops importing xrproducts. The workspace has folded packages before (xrcore, xrgrad, xreinx and xrsklearn went into xrops), so this would be the one package that earns its place by holding the floor.

xrtoolz still sits on top of geotoolz: xrops's calculus runs on geoops's difference kernels, and xrops.lift runs any geoops Operator item by item over a cube.

radiomax and radtrax: where the line is

radiomax converts and locates what the sensor saw; radtrax explains why it saw it.

The test: does the computation need a model of radiation moving through the atmosphere (absorption and scattering along a path, spectroscopy, an atmospheric state)? Then it is radtrax. Is it geometry, a unit conversion, or an empirical formula with fitted coefficients applied pixel by pixel? Then it is radiomax.

Why they sit in different layers. radtrax is a forward model: it has a state you can retrieve (profiles, surface, gas columns), which makes it GeoModels. radiomax has no state; it is maths on arrays, which makes it GeoNumerics. The import goes one way, radtrax → radiomax, so anything in radiomax that seems to need radiative transfer belongs in radtrax instead.

Grey zones, settled by the same test

  • Kernel BRDF comes from radiative-transfer approximations, but it is used as fixed kernels with fitted weights. No path, no atmospheric state: radiomax.
  • SRF convolution splits by what is being convolved. A band's effective coefficients are radiomax; a modelled high-resolution spectrum is radtrax's instrument model.

Today

The boundary is not clean in the code yet. Geometry and radiometry live in geoops, with copies in radtrax and plumax; brightness temperature alone is written three times in geotoolz. Building radiomax is mostly collecting those copies into one place, then pointing geoops, radtrax and plumax at it.

functax and geonnax: where the line is

functax says what a function family is and how to compute with it; geonnax says how to stack function families into a network.

The test: is it a function of coordinates used as an expansion, f(x) = Σⱼ cⱼ φⱼ(x; θ), together with its maths (evaluate, differentiate, transform, integrate, project, solve for c)? Then it is functax. Is it a stack of nonlinear layers, a map between fields, or a neural field, where the architecture is the point? Then it is geonnax.

Learned parameters are allowed on both sides. A basis can carry trainable θ: RBF centres and widths, Gabor and Fourier-feature frequencies, a Slepian region. functax keeps θ as ordinary pytree leaves, so gradients flow and anyone can fit them; it ships no network conventions (initialisation schemes, layer specs, depth). Whether θ is learned does not decide the side; whether the thing is an expansion or a network does.

Why split now. geonnax describes itself as a network zoo, but a third of it (about 3.5k lines in _basis) is bases "shared by NN spectral layers and GP inducing features", and that is what most of its users import. kernellib imports only bases, sphere grids, random features and lon/lat helpers; vardax and sesmax-core import only geonnax.basis; pyrox-gp re-exports geonnax's bases and keeps only the kernel-aware pieces. pyrox-nn is the one library that uses geonnax as a network library. Four of five users depend on a network zoo for maths.

What it changes in the graph

  • geonnax moves to Core tier 1, because it now imports functax (tier 0).
  • kernellib, vardax, sesmax-core and pyrox-gp import functax instead of geonnax. kernellib's import of geonnax is the one that already breaks the layer rule in the proposed layers (both are tier 1); it goes away with the move.
  • pyrox-nn becomes geonnax's one consumer in the stack; applications are the rest.
  • pyrox-nn stops importing pyrox-gp. Its three imports from pyrox-gp were bases (geonnax's, re-exported), a kernel's spectral density (kernellib maths) and the prior-freezing helper (pyrox machinery). With each taken from its home, pyrox-gp and pyrox-nn are siblings at Core tier 2.

Grey zones

  • A single SIREN layer is sin(Wx + b), which looks like a Fourier feature with learned frequencies. One fixed-width feature map with its maths is functax; SIREN as an architecture, with its initialisation scheme and depth, is geonnax.
  • Encoders are thin enough to move to functax, but they encode network conventions rather than maths, so they stay.
  • The ellipsoid. Core cannot import geophysix, so anything that needs WGS84 takes the constants as arguments. An encoder that insists on a default ellipsoid is a geo adapter and belongs above GeoNumerics.

The four layers, and the test for each

Three kinds of function, three kinds of data

This part now has its own working page, Kinds and roles. It holds the problem (why geo code is hard to write well), the objects in symbols, the role ladder from ⓪ structures to ⑥ recipes with orchestration above it, who works where, one vocabulary per axis, and the four rules: the cell decides the layer, the tier decides what a library may import, the kind and the data decide what a name may take and call, and each library declares its cells.

In short: code is packaged as a function, a Module or an Operator, and sees arrays, named arrays or carriers. Functions and Modules live as low as their imports allow, on plain arrays; Operators on carriers live where the carriers are. A carrier never goes below GeoStack, and a config never reaches a function. The rung chips on the cards above (⓪ to ⑥) come from that page's ladder.

Which foundations each library leans on

Each cell counts the import statements of that foundation in the library's source. lineax, optimistix and diffrax are core to the numerics and models; GeoStack lean on NumPy, rasterio, Shapely and pyproj instead. The functax row is the plan, not code.

Judgement calls

  1. Data assimilation. vardax and filterax import only Core, so the test puts them there. If you read DA as geophysical state estimation, they move up to GeoNumerics.
  2. geonnax. The name says geo, but its encoders and sphere grids are maths on the sphere, which passes the Core test.
  3. xtremax. Its "spatiotemporal data extraction" belongs in GeoStack if it reads products or CRS data; the modelling stays in Core.
  4. One diagnostics library, not two. Physical diagnostics need statistics (eddy kinetic energy and eddy fluxes are built on anomalies) and spectral statistics need kinematics (spectral fluxes use velocities), so a split would make each import the other. diagnostix holds both, in submodules: kinematics, column, budgets, stats, spectral, modes, skill. What goes in: a quantity derived from a geophysical field, physical or statistical, that needs area weights, a calendar or a constant; signal processing that needs none of these is functax's.
  5. Eulerian or Lagrangian. finitevolX and spectraldiffx hold operators on fields, whose state stays on the grid; tracerax holds positions carried forward in time and the analysis of their trajectories. Semi-Lagrangian advection traces a departure point for one step and discards it, so it stays with the field schemes. FTLE needs the flow map, so it is tracerax's; Okubo–Weiss uses the instantaneous field, so it is diagnostix's. The two sides never import each other: a model couples them through velocity in and concentration out.
  6. spectraldiffx. Its package description is stale ("Pre-, Geo-, and ML processing for ocean applications") and should say what it does.

What re-layering costs

  • The layer table and tiers in scripts/dependency_graph.py, and the diagram it generates.
  • One capability index per layer: Core replaces GeoML.
  • The pixi environments: geoml becomes core, or merges into the default.
  • Five imports go away, each by a move planned on this page: kernellib and pyrox-gp take bases from functax instead of geonnax (the geonnax split); pyrox-nn takes bases, spectral densities and prior freezing from functax, kernellib and pyrox instead of pyrox-gp; the pyrox core stops importing gaussx, because last-layer Laplace moves to pyrox-nn; and geoproducts stops importing geoops (its presets become data). Every other import found today fits as it is, with vardax at Core tier 4, above pipekit-jax, and gridax at GeoNumerics tier 1, above geophysix, whose cell areas it uses.
