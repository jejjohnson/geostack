GeoStack · background · L0 → L5

What has to happen between detector counts and a heatwave warning?

Earth-observation data are sorted into levels, from raw instrument output to finished indicators. This page is about the arrows between the levels: what each transition does to the data, what kind of operator performs it, and what software that operator needs underneath. One variable, sea surface temperature, is simulated from counts to heatwave events and scored against a known truth at every level.

TL;DR

Five transitions, five kinds of operator

  • Each transition changes one thing: units (L0→L1), meaning (L1→L2), geometry and completeness (L2→L3), time (L3→L4), and the question being answered (L4→L5).
  • Each is a different kind of operator. Calibration is a lookup per detector; retrieval is an inversion per pixel; gap-filling is one global solve per map; assimilation is a cycle that needs yesterday's result; derivation is a reduction over years that ends in a table.
  • The data change shape once. Up to L2 they keep the sensor's geometry (a swath: every pixel has its own position). From L3 they sit on a shared grid (a cube). Reading, indexing, carrying and transforming all differ on the two sides.
  • Accuracy and completeness trade. Here L2 is right to 0.19 K but covers 31% of the map on a given day; L3 covers everything at 0.47 K; L4, with dynamics, 0.27 K.
  • Every level must carry its uncertainty forward, since the next operator needs it: the L3 variance is the L4 observation error.
  • The test: the heatwave found from L4 matches 68% of the true heatwave cell-days (97% of what it flags is real); from L3 alone, 34%.

The levels

The names and numbers are those of the stack's overview. They follow the agencies' convention up to L2 and differ above it, so check which scheme a product uses before comparing labels.

L0 → L1 · read and calibrate: undo the instrument

The detector reports integers. Calibration turns them into a physical radiance with a gain and an offset per channel, and geolocation works out where each pixel was looking from where the satellite was and how it was pointed. No science choice is made here; the operator is fixed by the instrument.

def calibrate(counts, calibration):
    """L0 → L1: counts to brightness temperature, per channel."""
    # L = g · DN + o
    radiance = einx.add(                                        # (D, C, S, P) → (D, C, S, P)
        "d c s p, c -> d c s p",
        einx.multiply("d c s p, c -> d c s p", counts.astype(np.float64), calibration.gain),
        calibration.offset,
    )
    # T_b = c₂ / (λ ln(1 + c₁ / (λ⁵ L)))
    wavelength = einx.rearrange("c -> 1 c 1 1", WAVELENGTH_UM)
    brightness = inverse_planck(radiance, wavelength)           # (D, C, S, P) K
    return brightness
What the software has to solve
  • Parameters that change with time. Detectors drift, so gain and offset are a table indexed by date, not two numbers. When the table is revised, the whole archive is reprocessed and reissued under a new version (a “collection” or “baseline”). The operator must record which table it used.
  • Joining by time. Geolocation needs orbit, attitude and a terrain model, each a separate file found by timestamp. That join is most of the work.
  • Granules. Data arrive as a stream and are cut into files by time. The file is the unit of work, and neighbouring files overlap or abut.
  • Native geometry is kept. The output is a swath with per-pixel positions, never a map. Resampling this early would smear what later steps need.

In the wider world this is the space agencies' ground-segment software, one processor per instrument. Users rarely write it; they need readers that apply the stored coefficients correctly (GDAL and rasterio drivers, SatPy readers, h5py and netCDF4). In the stack: georeader and geoproducts readers, and operators such as DNToReflectance.

L1 → L2 · retrieve: from what was seen to what is there

The sensor saw the sea through an atmosphere that absorbed part of the signal: the 11 µm brightness temperature is 1.46 K away from the true SST. Water vapour absorbs more at 12 µm than at 11 µm, so the difference between the two channels measures the atmosphere, and a three-coefficient formula removes it. The coefficients are fitted, on pixels matched to buoys; the fit gives 1.63 for the channel-difference weight where the simulated physics says 1.67.

def fit_split_window(brightness, reference):
    """Fit θ on matchups: SST ≈ θ₀ + θ₁ T₁₁ + θ₂ (T₁₁ − T₁₂)."""
    t11, t12 = brightness
    design = np.column_stack([np.ones_like(t11), t11, t11 - t12])         # (M, 3)
    # θ = argmin ‖Aθ − y‖²
    theta, *_ = np.linalg.lstsq(design, reference, rcond=None)         # (3,)
    residual = reference - design @ theta                              # (M,) K
    return theta, float(residual.std())


def retrieve(brightness, theta, cloud_limit=270.0):
    """L1 → L2: brightness temperatures to SST, with a cloud flag."""
    t11 = brightness[:, 0]                                      # (D, S, P) K
    t12 = brightness[:, 1]
    # cloud test: a sea surface is never this cold
    clear = t11 > cloud_limit                                   # (D, S, P) bool
    # SST = θ₀ + θ₁ T₁₁ + θ₂ (T₁₁ − T₁₂)
    sst = theta[0] + theta[1] * t11 + theta[2] * (t11 - t12)    # (D, S, P) K
    return np.where(clear, sst, np.nan), clear
What the software has to solve
  • A forward model, or a regression that stands in for one. A full retrieval simulates the radiance for a guessed state and adjusts the guess (optimal estimation). The formula here is the cheap end of the same idea.
  • Per-pixel and independent. Each pixel is its own small inverse problem, so the work splits freely over pixels and granules. The cost is in the forward model, which is why lookup tables and learned emulators exist.
  • Outside information per scene. Angles, pressure, water vapour, a prior: the u row. Empty here; in a real retrieval it is a weather analysis joined in space and time.
  • Two phases. Fitting θ needs matchups with independent measurements and is done rarely; applying θ is done on every granule. They are different operators with different inputs.
  • Flags and error bars per pixel. A retrieval that fails must say so; a retrieval that succeeds must say how well.

In the wider world: operational algorithms are specified in algorithm theoretical basis documents; examples are split-window SST, Sen2Cor for Sentinel-2 surface reflectance, and the full-physics methane retrievals for TROPOMI. Radiative-transfer codes such as libRadtran, VLIDORT and MODTRAN supply the forward model. In the stack: radtrax, with geoops for the per-pixel operators.

L2 → L3 · grid and gap-fill: change the geometry, fill the holes

Two different jobs share this arrow. Binning moves swath pixels onto the grid by averaging those that fall in each cell: local and cheap. Gap-filling estimates the cells nothing saw from the ones something did, using how strongly nearby cells vary together: one linear solve over the whole map. The result is complete, and comes with a variance that is small where there were observations and large where there were not.

def bin_to_grid(sst, x, y):
    """L2 → L3, step 1: average the clear pixels that fall in each grid cell."""
    row = np.floor(y / CELL_KM).astype(int)
    col = np.floor(x / CELL_KM).astype(int)
    inside = np.isfinite(sst) & (row >= 0) & (row < GRID) & (col >= 0) & (col < GRID)
    index = row[inside] * GRID + col[inside]
    total = np.bincount(index, weights=sst[inside], minlength=GRID * GRID)
    count = np.bincount(index, minlength=GRID * GRID)
    mean = np.where(count > 0, total / np.maximum(count, 1), np.nan)
    return einx.rearrange("(y x) -> y x", mean, y=GRID), einx.rearrange("(y x) -> y x", count, y=GRID)


def gap_fill(binned, count, climatology, covariance, obs_std):
    """L2 → L3, step 2: optimal interpolation of the anomalies onto every cell."""
    observed = np.flatnonzero(count.ravel() > 0)                # (M,)
    innovation = (binned - climatology).ravel()[observed]       # y − H x_b      (M,)
    obs_variance = obs_std**2 / count.ravel()[observed]         # R diagonal     (M,)
    cross = covariance[:, observed]                             # B Hᵀ           (N, M)
    system = covariance[np.ix_(observed, observed)] + np.diag(obs_variance)   # H B Hᵀ + R
    # x̂ = x_b + B Hᵀ (H B Hᵀ + R)⁻¹ (y − H x_b)
    weights = np.linalg.solve(system, innovation)               # (M,)
    mean = climatology.ravel() + cross @ weights                # (N,) K
    # v̂ = diag(B − B Hᵀ (H B Hᵀ + R)⁻¹ H B)
    solved = np.linalg.solve(system, einx.rearrange("n m -> m n", cross))   # (M, N)
    reduction = einx.dot("n m, m n -> n", cross, solved)                    # (N,)
    variance = np.diag(covariance) - reduction                  # (N,) K²
    return einx.rearrange("(y x) -> y x", mean, y=GRID), einx.rearrange("(y x) -> y x", variance, y=GRID)

Measured: on cells that were observed, L3 is right to 0.07 K (averaging several pixels beats one); on cells that were not, 0.57 K, against 0.85 K for climatology alone.

What the software has to solve
  • The grid is an object. Projection, origin, spacing and extent are an explicit input, shared by every product that should line up.
  • The resampling rule depends on the variable. Average a temperature, conserve a flux, take the nearest value of a flag. One kernel for everything is a bug.
  • A global solve that does not fit. Gap-filling couples every cell to every observation: here a 4 096 × 4 096 covariance. Real maps need tiles with overlap, a limited radius of influence, or an iterative solver.
  • Variance out, not only a mean. A filled cell is a guess, and the next level needs to know how good.
  • Several sources meet here. Other satellites and in-situ measurements enter at this step, matched in space and time.

In the wider world: pyresample, GDAL's warp and ESMF/xESMF do the geometry; optimal interpolation produces the operational SST and sea-level maps (OSTIA, DUACS); DINEOF and kriging are alternatives, and neural gap-fillers are judged against them. In the stack: geoops for reprojection and compositing, the GeoML layer (kernellib, pyrox, the optimal interpolation of vardax) for the fill, geopatcher for the tiling.

L3 → L4 · model and assimilate: connect the days

Each L3 map uses one day's data. But the ocean has memory: yesterday's warm water is still there today, a little further east. A model carries yesterday's estimate forward; assimilation corrects that forecast with today's L3, trusting each in proportion to its variance. Cells under cloud today keep what was learned when they were clear.

def assimilate(analysis_l3, variance_l3, climatology):
    """L3 → L4: a forecast-analysis cycle with a per-cell Kalman filter."""
    state = np.zeros((GRID, GRID))                              # anomaly, K
    spread = np.full((GRID, GRID), ANOMALY_STD**2)              # its variance, K²
    states, spreads = [], []
    for day in range(DAYS):
        # forecast: x_f = ρ · shift(x_a);  P_f = ρ² · shift(P_a) + (1 − ρ²) σ²
        state = PERSISTENCE * np.roll(state, 1, axis=-1)
        spread = PERSISTENCE**2 * np.roll(spread, 1, axis=-1) + (1 - PERSISTENCE**2) * ANOMALY_STD**2
        # analysis: K = P_f / (P_f + R);  x_a = x_f + K (y − x_f);  P_a = (1 − K) P_f
        gain = spread / (spread + variance_l3[day])
        state = state + gain * (analysis_l3[day] - climatology - state)
        spread = (1 - gain) * spread
        states.append(climatology + state)
        spreads.append(spread)
    return np.stack(states), np.stack(spreads)                  # (D, Y, X) K, K²

Measured: error over all cells drops from 0.47 K to 0.27 K, and on unobserved cells from 0.57 K to 0.32 K. Running the model on without data gives a forecast: 0.39 K after one day and 0.52 K after five, against 0.90 K for climatology.

Watch out

This example assimilates the L3 analysis, with its variance as the observation error. The errors of an analysis are correlated from cell to cell, and treating them as independent counts some information twice. Operational systems assimilate L2 or L1 directly for that reason, through an observation operator.

What the software has to solve
  • State. The operator needs its own previous output. Days cannot be processed independently or out of order; a run is restarted from a saved state, and a failure on day 30 blocks day 31.
  • A model that is a program of its own. Often a large simulation code on a supercomputer, with its own grid, restart files and time step. The surrounding software feeds it and reads it.
  • The observation operator. A function from model state to what an instrument would have seen. It is the retrieval's forward model again, which is why the two should share code.
  • Error covariances. How wrong is the forecast, and where? Estimated from an ensemble of runs or fixed in advance; here one variance per cell.
  • Reanalysis is this, frozen. The same system run over decades without changing it, so that changes in the output are changes in the world.

In the wider world: variational methods (3D-Var, 4D-Var) and ensemble Kalman filters, in frameworks such as JEDI, DART and PDAF; products such as ERA5, GLORYS and the CAMS reanalysis; cycling workflow managers such as ecFlow and Cylc. In the stack: somax and plumax for models, filterax and vardax for assimilation, pipekit's cycles to run them.

L4 → L5 · derive: answer a question

Nobody asks for a temperature field; they ask whether there is a heatwave. A derived product applies a definition: here, warmer than the local 90th percentile for at least five days in a row. The output is first a mask, then a list of events with a start, a duration, a peak and an area.

def heatwave_mask(sst, threshold, min_days=5):
    """L4 → L5, step 1: above the 90th percentile for at least five days running."""
    hot = sst > threshold                                       # (D, Y, X) bool
    run = np.zeros(hot.shape, dtype=int)
    for day in range(hot.shape[0]):
        previous = run[day - 1] if day else 0
        run[day] = np.where(hot[day], previous + 1, 0)
    # a day belongs to a heatwave if its run reaches min_days at some point
    longest = run.copy()
    for day in range(hot.shape[0] - 2, -1, -1):
        longest[day] = np.where(hot[day] & hot[day + 1], np.maximum(longest[day], longest[day + 1]), longest[day])
    return hot & (longest >= min_days)


def heatwave_events(mask, sst, climatology):
    """L4 → L5, step 2: connected regions in (day, y, x) become rows of a table."""
    labels, count = scipy.ndimage.label(mask)
    events = []
    for event in range(1, count + 1):
        days, rows, cols = np.nonzero(labels == event)
        intensity = (sst - climatology)[days, rows, cols]
        area = np.bincount(days).max() * CELL_KM**2
        events.append({
            "start_day": int(days.min()), "end_day": int(days.max()),
            "duration_days": int(days.max() - days.min() + 1),
            "peak_intensity_K": round(float(intensity.max()), 2),
            "max_area_km2": int(area),
        })
    return sorted(events, key=lambda e: -e["max_area_km2"])

What the software has to solve
  • A long baseline. The threshold is a statistic over decades. Computing it is a reduction along time over the whole archive, done once and stored as a product of its own.
  • Definitions are parameters. The percentile, the minimum duration and the allowed gap are conventions that differ between communities. They belong in the configuration, and on the product's record.
  • The output stops being a field. Events are rows in a table or polygons on a map. The carrier changes a second time, from arrays to tables.
  • Small errors flip decisions. A threshold turns 0.3 K of error into a missed day, and a missed day ends a heatwave. Uncertainty has to reach this step too.

In the wider world: xclim and the ETCCDI climate indices; the marine heatwave definition of Hobday and colleagues (2016), used here; extreme-value statistics for return levels; impact and risk models downstream. In the stack: xtremax, with xrtoolz for the reductions.

This is why one pipeline framework has to offer more than “map a function over files”: a per-pixel map, a tiled solve, a stateful cycle and a reduction over time are four different shapes of computation.

Why the data change shape between L2 and L3

Three jobs stay whole across the dashed line because they do not depend on the shape: storage (bytes are bytes), patching (cut and stitch works on any field) and composition (an operator is an operator). The other four split, and a stack that pretends otherwise ends up resampling too early or carrying per-pixel coordinates it no longer needs.

Six design ideas that recur

  • Type operators by level. “L1 in, L2 out” is a signature. It says which operators may follow which, and lets a catalog record what a product is.
  • Make outside information an explicit input. Orbit files, weather fields, baselines: if an operator fetches them itself, the result cannot be reproduced. Pass them in, and record which were used.
  • Separate fitting from applying. Calibration tables, retrieval coefficients, covariance models and thresholds are produced rarely by one operator and used constantly by another. Version them like data.
  • Carry uncertainty and flags with the values. Every level here hands the next an error estimate; without the L3 variance the L4 update has nothing to weigh.
  • Name the unit of independent work. Granule, pixel, tile, ensemble member, grid cell: it differs per transition, and it decides how the computation is spread over machines.
  • Publish every level, not only the last. Each level is someone's input, and reprocessing restarts from the lowest level that changed. This is the loop of the geo pipeline, once per level.
