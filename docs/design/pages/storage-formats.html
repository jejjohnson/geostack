GeoStack · storage background · bytes → array

How does a 100 × 100 window come out of a 60 MB band?

Pictures first, maths folded away. Every cloud-native format answers the same question: given the pixels you want, which bytes do you fetch? COG, GeoParquet and Zarr each answer it with an index. kerchunk, VirtualiZarr and Icechunk separate that index from the files, so one set of bytes can be read as Zarr, combined with others and versioned.

TL;DR

Four indexes over the same bytes

  • A COG is a GeoTIFF whose header lists where every tile starts and how long it is, so a window read is a few HTTP range requests, not a download.
  • GeoParquet is a table stored by column and by row group, with per-group bounding boxes and times, so a query skips most of the file.
  • Zarr splits an N-dimensional array into chunks, one object per chunk key, described by small JSON metadata files.
  • A chunk reference (URL, offset, length) is all a Zarr reader needs. kerchunk writes references to a file, VirtualiZarr builds them from archives as xarray objects, and Icechunk stores them, with real chunks, in versioned commits.
  • Reading a raster through Icechunk is a Zarr key lookup, then a manifest lookup, then the same range request a COG read makes. The test: the bytes fetched for our window are identical in both paths.

Part 1 · Three formats, three indexes

COG: a GeoTIFF you can read in pieces

Our band is one file of 60.3 MB. A plain GeoTIFF stored in strips, or with its header at the end, forces a reader to fetch most of it to find anything. A Cloud-Optimized GeoTIFF puts the header first, stores the image in square tiles, and adds downsampled overviews, so the header alone says exactly which bytes hold which pixels.

  1. Read the header, a few kilobytes at the start of the file.
  2. Work out which tiles the window touches, by dividing pixel positions by the tile size.
  3. Fetch only those tiles, one byte range each, and decode them.
# Shapes: C bands; window of H × W pixels; T tiles touched
# Units:  [DN] = Sentinel-2 L2A digital number; [B] = bytes
import geoarray
import geocloud.cog

# today (geocloud)
source = geocloud.cog.CogSource.open(b12_url)                   # header only  ≈ kB
# today (geoarray)
window = geoarray.PixelWindow(                                  # → (4,)  px
    col_off=3050, row_off=2000, width=100, height=100
)
# k = i n_t + j for (i, j) ∈ 𝓘 × 𝓙; x_W = crop(decode(GET(url, [o_k, o_k + ℓ_k))))
# today (geocloud)
site = source.read_window(window)                       # → (1, 100, 100)  [DN]
Watch out

The tile size, not the window, sets the cost: our 100 × 100 window straddles four tiles and fetches about a hundred times the bytes it uses. A COG made for small windows uses smaller tiles, and the original Sentinel-2 archive (JPEG 2000 in SAFE folders) is not a COG at all, which is why catalogs such as Earth Search republish it as COGs.

Running example

Our site window touches tiles 38, 39, 49 and 50 of B12: one header read and four range requests, at most 2.1 MB before compression, instead of 60.3 MB.

When to use a COG

Use a COG when the unit of work is one image on one grid, and other people or tools need to open it. Every GIS, GDAL, rasterio and the web tilers read COGs directly, with no extra library.

  • Per-scene L1 and L2 products: Sentinel-2 L2A and Landsat Collection 2 are published as COGs on AWS and Planetary Computer.
  • Your own per-scene outputs: a matched-filter enhancement map written with geocloud.cog.write_cog, handed to a colleague or a dashboard.
  • Map tiles on the fly: overviews let a tiler serve a zoomed-out view without reading full-resolution tiles.

Less suited to a time series on one grid (one file per date means one open per date), to more than three dimensions, or to data that grows by appending.

GeoParquet: a table you can read by column and by place

Before reading any pixel you need the six June scenes that cover the site. That is a table question: which rows have a footprint over \(B\) and a time inside \(\mathcal{T}\)? GeoParquet is Parquet with a standard geometry column, and it answers that question without reading the whole table.

Sorting decides how much a query skips. geocatalog's build_raster_catalog sorts rows by start_time, then by a Hilbert key of the geometry, by default, so rows close in time and space land in the same row groups.

# Shapes: R rows in the catalog; G row groups; S rows kept
# Units:  bounds in the catalog CRS [m]; times naive UTC
import geocatalog

# today (geocatalog)
catalog = geocatalog.open_catalog("s3://bkt/s2_l2a.parquet")    # footer only → R rows
# keep_g ⇔ b_g ∩ B ≠ ∅ ∧ τ_g ∩ 𝒯 ≠ ∅, then the same test per row
# today (geocatalog)
june = catalog.query(site_june)                                 # R → S = 6 rows
Watch out

Without the bounding-box column (GeoParquet 1.0 files, or files written without it), the footer has no spatial statistics, so a spatial filter must decode every geometry. Write files with the covering column, and sort them, or the format's main advantage is lost.

Running example

The query reads the footer, the row groups whose time range overlaps June 2026, and only the geometry, time and filepath columns, and returns six rows: six COG paths for B12.

When to use GeoParquet

Use GeoParquet for anything that is a table with a geometry: one row per thing, a few columns per row. It is compact, typed, and queried in place by DuckDB, pandas, geopandas and browsers.

  • Catalogs of files or scenes: geocatalog saves every catalog as GeoParquet and queries it with DuckDB.
  • Vector products: plume outlines, areas of interest, field boundaries.
  • Point observations and matchups: Argo profiles, along-track sea-surface height, station series, scene-to-in-situ matchup tables.

Not for dense rasters: a grid stored as one row per pixel is large and slow; keep pixels in COG or Zarr and their footprints in GeoParquet.

Row-group skipping in symbols
Concept

Parquet stores a table by column and by row group

Rows are cut into row groups; inside a group each column is stored on its own, and the file footer keeps each column's minimum and maximum per group. A reader fetches only the columns it needs, and skips any group whose statistics cannot match. GeoParquet adds the geometry column (WKB) and, in version 1.1, a bounding-box column whose statistics make spatial skipping work:

\[ \mathrm{keep}_g \iff \vect{b}_g \cap B \neq \varnothing \wedge \tau_g \cap \mathcal{T} \neq \varnothing \]
Where \(g\)a row group, a few thousand to a million rows\(\mathbb{Z}_{\ge 0}\)— \(\vect{b}_g\)smallest box holding every footprint in group \(g\)\(\mathbb{R}^4\)m \(\tau_g\)earliest start and latest end time in group \(g\)intervaltime

Zarr: an array split into keyed chunks

A COG is one file with an internal index. Zarr turns the index inside out: each chunk is its own object, its name is computed from its position, and a small JSON file describes the array. Nothing has to be read to find a chunk; the key says where it is.

Version 3 adds sharding: many chunks packed into one object with a small index at its end, so a store need not hold millions of tiny objects.

# Shapes: H × W window; chunks of P × P
# Units:  [DN]
import xarray as xr

# not pinned (xarray)
band = xr.open_zarr("s3://bkt/b12.zarr")["B12"]                # zarr.json only
# κ_ij = B12/c/i/j for (i, j) ∈ 𝓘 × 𝓙
# not pinned (xarray)
site = band.isel(y=slice(2000, 2100), x=slice(3050, 3150))  # → (100, 100)  [DN]
# not pinned (xarray)
pixels = site.values                                            # reads 4 chunks  [DN]
Watch out

Chunk shape is fixed when the array is written and sets every read's cost, as tile size does for a COG. Chunks that are too small make millions of objects and requests; too large, and every small window fetches megabytes. Sharding exists to separate the two choices.

Running example

Stored as Zarr with \(512 \times 512\) chunks, B12 is 121 objects, B12/c/0/0 to B12/c/10/10, and the site window reads B12/c/3/5, c/3/6, c/4/5 and c/4/6: the same four tiles as the COG.

When to use Zarr

Use Zarr when the data is a cube: many dates, levels, bands or ensemble members on one grid, or anything that grows by appending. Chunks can be shaped for the reads you do most, along time for a pixel's series or along space for a map.

  • L3 and L4 grids: ERA5, GLORYS, gap-filled sea-surface height, your analysis cubes.
  • Model output and training data: a run appended step by step; pipekit's CachedDataset writes Zarr.
  • Many variables together: a Dataset or DataTree with shared coordinates, opened lazily by xarray.

Less suited to handing one scene to a GIS user, and to very small chunks: a million 1 kB objects cost a million requests unless you shard.

A Zarr array is metadata plus one object per chunk

COG and Zarr: what maps to what

A COG and a Zarr array store the same thing in the same way: a grid cut into compressed blocks, plus a small description. They differ in where the index lives (inside one file, or in the keys), in how many dimensions they allow, and in how georeferencing is written down.

Is it a one-to-one translation?

  • Pixels: yes, both ways. The values, data type, tile or chunk grid and nodata value carry over without loss.
  • Bytes: often, even without copying. A COG tile can be served as a Zarr chunk as-is, which is exactly what a virtual reference does, as long as a Zarr codec exists for the COG's compression. virtual-tiff lists Deflate, Zlib, LZW, LZMA, LERC, PNG, WebP, JPEG XL and PackBits; old-style JPEG TIFFs are not supported yet, so check a file's compression before relying on it.
  • Georeferencing: only through a convention. A COG stores its CRS and transform in GeoTIFF tags that every GIS reads. Zarr has no built-in georeferencing, so it lives in attributes: CF grid_mapping with a spatial_ref variable (what geoarray.to_xarray writes), the GeoZarr conventions, or your own. A reader that does not know the convention sees an array with no place on Earth.
  • Overviews and extra dimensions: not one-to-one. COG overviews become a multiscales group, one array per level, by convention. A Zarr cube with time or ensemble dimensions has no single-COG equivalent: it becomes one COG per time step and member.

Can Zarr read a COG directly?

Not by itself. zarr-python reads stores laid out as Zarr keys, and a COG is one file with its own index. Three bridges give a COG a Zarr face without converting it:

  • tifffile opens a TIFF or COG as a Zarr store (imread(path, return_as="zarr"), zarr-python 3), mapping its tiles to chunks on the fly. It can also write that mapping out as fsspec reference JSON.
  • virtual-tiff, a VirtualiZarr parser, turns the COG's tiles into virtual Zarr v3 references you can commit to Icechunk: the route Part 2 follows.
  • kerchunk scans a TIFF into a reference file that fsspec serves as Zarr.

In the other direction, GDAL's Zarr driver reads Zarr, so gdal_translate can write a Zarr array out as a COG.

Converting, with the stack

# Shapes: C bands; (y, x) = (5490, 5490); chunks and tiles of 512 × 512
# Units:  [DN]
import geoarray
import geocloud.cog
import geoops.io
import xarray as xr

# --- COG → Zarr, as a copy ---
# today (geocloud)
scene = geocloud.cog.CogSource.open(b12_url).load()            # → (1, 5490, 5490)  [DN]
# today* (geoops)
write = geoops.io.WriteZarr(store="s3://bkt/b12.zarr", chunks={"y": 512, "x": 512})
write(scene)

# --- Zarr → COG ---
# not pinned (xarray)
band = xr.open_zarr("s3://bkt/b12.zarr")["B12"]
# today (geoarray)
grid = geoarray.from_xarray(band)                              # → (1, 5490, 5490)  [DN]
# today (geocloud)
geocloud.cog.write_cog(grid, "s3://bkt/b12_copy.tif")
Watch out

The two writers in the stack disagree on georeferencing today: geoops.io.WriteZarr stores crs and transform as plain attributes, while geoarray.from_xarray reads a CF spatial_ref. Until they share one convention (workstream D of the Level 2 collections doc), the Zarr → COG round trip above needs the CRS restored by hand.

The third route needs no copy at all: open the COG with VirtualiZarr's TIFF parser, and its tiles become Zarr chunks by reference. That is Part 2.

Part 2 · Pointers instead of copies

Look at boxes 1 and 3 again. A COG tile and a Zarr chunk are the same thing: a compressed block of pixels at a known place. A Zarr reader does not care whether the bytes of B12/c/3/5 sit in their own object or inside a COG, as long as it can find them. That observation is all three tools below are built on.

The reference in symbols
Concept

A chunk reference is where the bytes are, not the bytes

For every Zarr key, store a reference to bytes that already exist, and give the reader the codec chain to decode them:

\[ \mathrm{ref}(\kappa_{ij}) = (\mathrm{url}_k, o_k, \ell_k) \]

A set of references plus the array metadata is a virtual Zarr store: Zarr's interface over the original files, with nothing copied.

Where \(\mathrm{url}_k\)the original file holding tile \(k\)string— \(o_k, \ell_k\)the tile's offset and length in that file, from its header\(\mathbb{Z}_{\ge 0}\)B

kerchunk: references written to a file

kerchunk scans an archival file (HDF5, NetCDF, GRIB, TIFF) and writes its references to a JSON or Parquet file. fsspec's reference filesystem then serves the keys, so xarray opens the archive as if it were Zarr. kerchunk predates Zarr v3, so its keys use v2's dotted form.

# a kerchunk reference file, abbreviated: Zarr v2 keys → [url, offset, length]
{
  "version": 1,
  "refs": {
    "B12/.zarray": "{\"shape\": [5490, 5490], \"chunks\": [512, 512], ...}",
    "B12/3.5": ["s3://bkt/T30SYJ_20260601_B12.tif", o_38, ℓ_38],
    "B12/3.6": ["s3://bkt/T30SYJ_20260601_B12.tif", o_39, ℓ_39]
  }
}
Watch out

A reference file is just a file: nothing versions it, nothing updates it atomically, and one JSON file for millions of chunks grows large (hence the Parquet form). Two writers, or a crash mid-write, leave it inconsistent.

VirtualiZarr: references as xarray objects

VirtualiZarr opens an archival file with a parser for its format and returns an xarray.Dataset whose variables are ManifestArrays: arrays of chunk references, not of values. You can concatenate, merge and rename them with ordinary xarray calls, then write the result to kerchunk JSON or Parquet, or into an Icechunk repo. It has parsers for HDF5/NetCDF4, NetCDF3, TIFF, GRIB, FITS, DMR++ and existing kerchunk and Zarr stores.

# Shapes: S scenes; per scene one (y, x) band in n_t² chunks
# Units:  references only; no pixel values are read
import virtualizarr
import xarray as xr

# not pinned (virtualizarr)
scene = virtualizarr.open_virtual_dataset(                      # → 121 refs
    url=b12_url, parser=tiff_parser, registry=registry
)
# the six June scenes along a new time axis: only manifests are joined
# not pinned (virtualizarr)
june = xr.concat(scenes, dim="time")                            # → 726 refs
Watch out

Concatenation needs every input to share chunk shape, codecs and grid. Six revisits of one MGRS tile do; scenes from neighbouring tiles in different UTM zones do not, which is why Level 2 collections keep one group per scene instead of one cube.

Icechunk: a versioned store for real and virtual chunks

Icechunk is a storage engine for Zarr v3. A repository holds array metadata, chunks written into it, and references to chunks elsewhere, and every change goes through a transaction that ends in a commit. Each commit is a snapshot with an id; branches and tags name snapshots. Readers open a snapshot and see a consistent store, whatever writers are doing.

How a raster is read in chunks through Icechunk

This is the step the Level 2 collections design takes for granted. Write the six June B12 COGs into a repo as virtual references, then read the site window through Zarr. Five steps, and only one of them is new.

# Shapes: S = 6 scenes; per scene (y, x) = (5490, 5490) in 121 chunks; window 100 × 100
# Units:  [DN]; references in bytes
import icechunk
import xarray as xr

# --- write once: references, not pixels ---
# config names s3://bkt/ as a virtual chunk container
# not pinned (icechunk)
repo = icechunk.Repository.create(storage, config)
# not pinned (icechunk)
session = repo.writable_session("main")
# not pinned (virtualizarr)
june.vz.to_icechunk(session.store)                              # → 726 refs  refs
# not pinned (icechunk)
snapshot_id = session.commit("B12, June 2026, six scenes")     # → σ

# --- read any time later: Zarr keys → manifest → ranged GETs ---
# not pinned (icechunk)
reader = repo.readonly_session(snapshot_id=snapshot_id)
# not pinned (xarray)

# κ_ij → M_σ(κ_ij) = (url_k, o_k, ℓ_k) → GET → decode
# not pinned (xarray)
site = cube.isel(time=0, y=slice(2000, 2100), x=slice(3050, 3150))  # lazy
# not pinned (xarray)

Watch out

Virtual references only work while the original files stay where they are and stay byte-identical. Readers must also be allowed to fetch from the referenced URL prefix (Icechunk calls it a virtual chunk container), and how that is authorised depends on the Icechunk version; check the release you pin.

Running example

The repo holds 726 references and a few kilobytes of metadata, not 362 MB of pixels (six bands of 60.3 MB). Reading the site in one June scene fetches the same four tiles as the COG read; reading it in all six scenes fetches 24.

lazycogs and geocatalog

lazycogs does in one call what geocatalog does in two: search STAC, cache the hits as GeoParquet, then load a lazy cube on a target grid without GDAL. That overlaps load_raster_timeseries (which reads through rasterio) closely enough to be worth a look as an engine behind it, the way async-geotiff already sits behind geocloud.cog.

So should you write Zarr, or keep TIFFs and COGs?

  • Keep COGs for anything delivered per scene or opened in a GIS, and for archives others publish. Do not convert a mission's archive to Zarr just to read it: reference it.
  • Write Zarr when you produce a cube (many dates on one grid, model output, training data) or append over time. That is where Zarr's N-D chunks pay off.
  • Reference, don't copy, when you need Zarr's interface over files you do not own. VirtualiZarr builds the references; Icechunk keeps them, versioned, next to any real chunks you add.
  • Plain TIFFs that are not COGs (striped, header at the end) should be converted to COGs before cloud use; a virtual reference to a striped TIFF reads whole strips.
  • Remember the audience of Part 2. An Icechunk repo is not a plain Zarr folder: a reader needs the Icechunk client. For data you hand to people outside your stack, publish COGs or plain Zarr as well.
